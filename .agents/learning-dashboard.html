How a hand becomes music dwell → fire → play()

R1 sees your hands and reads each finger. R2 turns those jittery readings into deliberate commands: a shape, held inside a box, long enough, fires exactly once. R3 connects those commands to a track: open palm plays and pauses, index up restarts. This page explains the mechanism under each step and points at the real code.

How the pieces connect

One trip around this loop happens for every camera frame, about 30 times a second. Colour tells you who owns each step. The dotted row is R2, built on branch r2-gestures and not merged yet. The dashed row is R3, the audio, being written now on r3-audio.

What the R1 live test taught us

One wrong label flipped two readouts

What you saw

Left and Right came out swapped on the hand cards. At the same moment, palm-facing read "facing" when the back of your hand was toward the camera, and the other way round.

The fix

swapHandedness: false in src/config.ts:66 (commit 50517b6). It had been true, based on MediaPipe's documented assumption of a mirrored selfie image. Your real hand showed the unswapped label was already right.

What did not change

The finger readout (T0 I1 M1 R0 P0) was correct throughout. pseudoChord never reads the hand label (comment at src/pseudoChord.ts:35).

Why a wrong label inverts palm-facing. src/palmFacing.ts:38 builds the palm normal as the cross product of two vectors: wrist → index knuckle (landmark 5) and wrist → pinky knuckle (landmark 17). On a flat screen, the z part of that cross product only says one thing: going from the index knuckle to the pinky knuckle around the wrist, do you turn clockwise or counter-clockwise? It cannot say which hand it is looking at.

Why the unit tests didn't catch it. The tests check palmFacing given a correct label. One even proves the dependency: same landmarks, wrong hand, opposite answer (src/palmFacing.test.ts:43). What was wrong was an assumption about the outside world (how MediaPipe labels an un-mirrored frame), and only a real hand in front of a real camera can test that.

For R2: the spec's two-hand clutch tells the hands apart by which side of the screen they're on, not by the model's label (spec §5.2). This incident is the evidence for that choice. analyze.ts:58 already sorts hands by wrist x, which is the same idea.

Suppose swapHandedness were wrong again. You show a V with your right palm to the camera. What do the three readouts show: hand label, palm facing, and the chord?Reveal

Label: Left (wrong). Palm facing: no (wrong, inverted with the label). Chord: T0 I1 M1 R0 P0 (right). The chord uses distances and an angle, which come out the same whichever hand it is, so a wrong label cannot touch it.

Checkpoint R2 · active

R2: turning shapes into commands

R1 answers "what shape is this frame?" R2 has to answer "did the dancer deliberately make this shape, once, in the right place?" That second question is about history, time and space, not about one frame. Seven ideas make it work. The R2 code is being written on another branch, so this section is grounded in docs/spec.md §4.2–4.4 and §5.2 and the roadmap; look for the code in src/ once R2 lands.

R2 · Gesture logic

Finite state machines: idle → arming → fired → cooldown

Problem

Each frame, analyze() hands you a fresh reading with no memory of the last one. A command needs memory: how long has this shape been up, did it already fire, has the hand dropped since?

Naive fix

Put if (shape === "Open_Palm") togglePlay() in the frame loop. At 30 fps a one-second palm toggles play 30 times. The next naive fix is a handful of booleans (isHolding, hasFired, inCooldown, startedAt). Five booleans allow 32 combinations, most of which should be impossible, and bugs live in those combinations.

Mechanism

A finite state machine keeps the gesture in exactly one named state. Once per frame a step function looks at three things (the current state, this frame's input, the current time) and either stays put or follows one of a few allowed arrows. Side effects, such as firing a command or playing a sound, happen only on particular arrows.

shape present (in box, palm facing, one hand) IDLE ───────────────────────────────────────────► ARMING t0 = now, ring fills ▲ │ shape lost longer than grace ──► IDLE │ │ now − t0 ≥ 0.6 s │ ▼ │ FIRE (one frame: banner, sound, log) │ │ └──────── 1.0 s passed AND shape released ◄──── COOLDOWN
  • Time comes from timestamps, not frame counts. main.ts:79 already computes ts = performance.now() for the model. "18 frames" is 0.6 s at 30 fps, but 1.2 s at 15 fps in a dim room.
  • "No hand" is an input. When the hand leaves the view, frames keep arriving with an empty result. The step function must treat that as "shape lost". If it only ran when a hand was present, the machine would sit in ARMING forever.
  • Cooldown exits on two conditions. Time alone is not enough: a palm held for 4 s would fire again at 1.6 s. Requiring a release too gives "holding a shape a long time fires exactly once" (roadmap R2 done means).
  • Keep it pure. step(state, input, now) → { state, events } touches no camera and no DOM, so Vitest can feed it a scripted timeline and assert exactly one event, in the same style as src/pseudoChord.test.ts.
In Dance

Spec §4.2 sets the guards: palm centre in the command box, shape held 0.6 s, palm facing, 1.0 s cooldown, only one hand showing a command shape. The optional stillness rule (off by default) is one more guard on the IDLE → ARMING arrow, not a new boolean. Remembering t0 pays off in R4, where loop marks are stamped at the moment the ring started, minus 0.15 s (spec §4.6).

Tradeoff
  • Cost: more structure up front than a single if. Gain: every behaviour is an arrow you can point at, and impossible combinations can't happen.
  • Failure mode: a missing arrow becomes a stuck state, for example a lost hand that never returns the machine to IDLE. It shows up as "it stopped responding until I reloaded".
You hold an open palm in the box for 4 seconds, then drop it. How many times does play/pause toggle, and which part of which arrow blocks a second fire?Reveal

Once, at 0.6 s. The machine enters COOLDOWN. At 1.6 s the "1.0 s passed" half of the exit arrow is satisfied, but the "shape released" half is not, so it stays in COOLDOWN until you drop the hand at 4 s. Try the "Long hold" preset in the timeline lab with the gesture set to Open palm.

R2 · Gesture logic

Dwell: hold to confirm

Problem

Choreography passes through command shapes all the time: an arm sweep shows an open palm for a fraction of a second. The recognizer also misreads a frame here and there. Either one would fire a command by accident.

Naive fix

Fire on the first frame the shape appears. Every pass-through and every one-frame misread becomes a command.

Mechanism

Require the condition to hold continuously for a dwell time before acting. The ring is that requirement drawn on screen: progress = (now − t0) / 0.6 s.

  • Why it works on misreads. If a single frame is wrongly read as an open palm with probability p, and frames were independent, 18 wrong frames in a row (0.6 s at 30 fps) would have probability p18. With p = 0.1, that is 10−18. Real errors are correlated, so the real number is much higher, but the effect is still large.
  • Why it works on pass-throughs. A sweep shorter than 0.6 s never finishes the ring.
  • Where it does not help. A choreography pose that really is an open palm, held still in the box for a second, looks exactly like a command. Dwell filters short and flickery signals, not deliberate-looking ones. That is the spec's unresolved "choreography collides with commands" thread.
  • Grace period. One or two dropped frames in the middle of a real hold shouldn't reset the ring. A short grace (around 0.1 s) lets the shape vanish briefly without counting as lost. Too long, and two separate gestures merge into one.
In Dance

0.6 s minimum dwell, tunable up with a slider (spec §4.2, roadmap R2 scope). The roadmap's informational test (dance about 2 minutes with no commands intended, count false fires in the log) is the data for tuning it.

Tradeoff
  • Latency on purpose: every command arrives at least 0.6 s after you make the shape. In R3 that dominates the delay budget by design. The ring makes the wait visible, so it feels deliberate rather than laggy.
  • Longer dwell: fewer false fires, slower commands. Shorter: the reverse.
An arm swing passes an open palm through the box for 0.3 s, five times in one phrase. Then, later, the choreography holds an open palm still in the box for 2 s. Dwell is 0.6 s. How many fires in total?Reveal

One. None of the 0.3 s passes completes the ring (the lab's "Dance move passes through" preset). The 2 s pose completes it at 0.6 s and fires, and cooldown blocks a second fire until the hand drops. Dwell can't tell a held pose from a command; the box, a longer dwell, or the stillness rule are the levers for that.

R2 · Gesture logic

Debouncing and hysteresis: why readouts flicker near a threshold

Problem

Every number the model gives you carries noise. When the true value sits near a threshold, noise pushes each frame randomly over or under it, so the readout flips at up to 30 times a second. R1's finger rule has a single threshold: extended when the tip/PIP distance ratio is at least 1.08 (src/config.ts:39, used at src/pseudoChord.ts:49). A half-bent finger sitting at 1.08 flickers.

Naive fix

Move the threshold. The flicker moves with it, to whichever hand pose now sits at the new line.

Mechanism

Two separate tools, working on two different axes.

  • Hysteresis works on the value axis. Use two thresholds: switch on above the high one, switch off below the low one, and in between keep whatever you were. A thermostat works this way (heat on at 19°, off at 21°). The gap, called a dead band, should be wider than the noise. Note what this costs: the output now depends on the previous output, so it is state, not a pure function of one frame.
  • Debouncing works on the time axis. Accept a change only after it has lasted a set time. The name comes from mechanical switches, whose contacts bounce for a few milliseconds. Dwell is a debounce on the "on" edge; the grace period is a debounce on the "off" edge.
  • Smoothing (an exponential moving average, avg = α·x + (1 − α)·avg) shrinks the noise but adds lag, and a smoothed value can still hover at a single threshold.

Distance makes all of this worse. Two metres back, your hand is a few dozen pixels tall and the model's pixel-level jitter is a bigger fraction of every ratio.

In Dance

Spec §5.2 asks for hysteresis on pinch: "below a threshold = grabbed; it must clearly open again to release". The same idea applies to a palm centre sitting on the edge of the command box, and to the shape score. R1's chord readout has none yet; check whether R2 adds it anywhere besides pinch.

Tradeoff
  • Too narrow a dead band: flicker returns. Too wide: sticky. A pinch that is hard to release, or a readout that lags the truth.
  • Debounce always adds latency equal to its window.
Shape score hovers between 0.50 and 0.70. On-threshold 0.60, off-threshold 0.45. With hysteresis off (single line at 0.60), and then on, does the 0.6 s ring ever complete?Reveal

Off: the score keeps dipping under 0.60, and each dip longer than the grace period resets the ring, so it may never complete. On: once the score crosses 0.60, it only switches off below 0.45, which it never reaches, so the ring fills and fires. Check it with the "Flicker near threshold" preset and the Hysteresis button in the lab.

R2 · Gesture logic

Tap vs hold: deciding needs the future

Problem

Three shapes, more actions. Looper pedals double their vocabulary by giving each switch one action on a tap and another on a hold (spec §4.4).

Naive fix

Decide when the dwell ring fills. At that moment you can't know whether the dancer is about to drop the hand or keep holding.

Mechanism

Defer the decision with one extra state. When the inner ring fills, go to ARMED and wait.

ARMING ──(0.6 s)──► ARMED ──(released before 1.5 s)──► fire TAP → COOLDOWN └──(still held at 1.5 s)──► fire HOLD → COOLDOWN
  • Tap fires on release, so it lands later by however long you held past 0.6 s, plus the grace period that confirms the release.
  • Hold fires the moment the outer ring fills, without waiting for release.
  • A gesture with no hold action skips ARMED and fires as soon as the inner ring fills, which keeps play/pause fast.

A mouse does the same thing for single vs double click: it can't report "single" until the double-click window has passed.

In Dance

Open palm: fires at the ring (spec §4.3). Index: tap = restart (song start in R3, loop start in R4), hold = song start. V: tap cycles the loop, hold clears it (R4). In R2 these only fire into the banner and log; nothing is controlled yet. Done means: tap and hold are told apart correctly on 9 of 10 attempts.

Tradeoff
  • Taps are slower than they look. The wishlist tracks this as "tap vs hold adds a short delay"; probably fine between attempts.
  • Lingering by accident turns a tap into a hold. The ring label (what will fire) is the defence.
Index up. The inner ring fills at 0.6 s; you keep holding until 1.2 s, then drop. Grace is 0.1 s. What fires, and when? And if you had dropped at 0.5 s?Reveal

TAP, at about 1.3 s (1.2 s release plus 0.1 s grace). Dropping at 0.5 s fires nothing: the machine was still ARMING, so losing the shape sends it back to IDLE.

    R2 · Space

    Hit-testing a point in a rectangle, across coordinate spaces

    Problem

    "Is the palm centre inside the command box?" takes one line of maths once both are in the same coordinate space. Dance has four spaces, and two of them are mirror images of each other.

    Naive fix

    Store the default box as "right half": x ≥ 0.5, and compare the landmark's x to it. The landmark is in the raw, un-mirrored frame, where x ≥ 0.5 is the left half of what you see. The box is drawn on your right, your hand there does nothing, and your left hand fires. Same family of bug as the handedness flip.

    Mechanism
    SpaceUnitsMirrored?Where in R1
    Landmark (raw)0..1 of the framenomodel output; analyze.ts, all geometry
    Canvas backing storevideo px, 1280×720no (CSS flips it)main.ts:68–71 sizes it; draw.ts:30 multiplies by width, height
    Display (what you see)0..1 of the pictureyes#mirror { transform: scaleX(-1) }, style.css:87
    Mouse (client)CSS px from the viewportas displayedpointer events (new in R2)
    1. Palm centre (spec §4.2) is the average of the wrist and the four finger knuckles: landmarks 0, 5, 9, 13, 17. It stays steady while fingers move.
    2. Raw → display: dx = 1 − x, dy = y. Mirroring only flips x.
    3. Mouse → display: u = (clientX − rect.left) / rect.width, same for v, where rect = el.getBoundingClientRect(). A scaleX(-1) around the element's centre leaves its bounding box where it was, so u is already in display space. R1's video isn't letterboxed (#mirror shrinks to fit the video), so no extra offset is needed.
    4. Pick one home for the box and convert everything else into it once. Display space is the natural home: it is what the mouse gives you and what "right half" means to you.
    5. The test: dx ≥ L && dx ≤ L + W && dy ≥ T && dy ≤ T + H.
    6. Drawing it: on the mirrored overlay canvas, draw at raw coordinates: raw left edge = 1 − (L + W). Any text drawn on that canvas comes out backwards, which is why R1 keeps readouts in HTML.
    In Dance

    Default box: the right half of the mirrored view; presets right half, left half, whole frame (spec §4.2). Store it as fractions, not pixels: fractions survive a window resize and a change of camera resolution.

    Tradeoff
    • Hard edge: a palm centre sitting on the box edge flickers in and out. A small margin (enter at the edge, leave a little outside it) is hysteresis applied to space.
    • Palm centre vs wrist: the centre is steadier but costs a five-point average. That is trivial next to the model call.
    Palm centre has raw x = 0.30. The box is the display's right half (x 0.5 to 1). Inside or outside? And what would code that forgot the flip decide?Reveal

    Display x = 1 − 0.30 = 0.70, so inside. Code that forgot the flip compares 0.30 to 0.5…1 and says outside. On screen, the hand looks clearly inside the box and nothing happens.

    R2 · Input

    Mouse drag and resize handles

    Problem

    Click and drag inside the box to move it; drag an edge or corner to resize it; the new area takes effect immediately (roadmap R2 done means).

    Naive fix

    On mousemove with the button down, set box.x = mouse.x. The box's corner jumps to the cursor. Drag fast, the cursor leaves the element, events stop arriving, and the drag gets stuck. Adding each event's small movement to the box instead lets rounding errors pile up into drift.

    Mechanism

    A three-phase pointer protocol.

    1. pointerdown: decide what was grabbed. Hit-test zones in priority order: corner handles (within about 10 CSS px of a corner), then edges (within about 8 px), then inside (move), then outside (ignore). Save the mode, the pointer's start position, and a copy of the box as it was. Call el.setPointerCapture(e.pointerId) so every later move event comes to this element even when the cursor leaves it.
    2. pointermove: recompute from the start. dx = now − start, in display fractions. Move: L = L₀ + dx. Left edge: L = L₀ + dx, W = W₀ − dx. Right edge: W = W₀ + dx. Corners combine one horizontal and one vertical edge. Then clamp to 0…1 and to a minimum size. Always computing from the saved box, never from the last frame, is what stops drift.
    3. pointerup / pointercancel: finish. Clear the mode. Capture is released automatically.

    On hover, set the cursor to match the zone (move, ew-resize, ns-resize, nwse-resize, nesw-resize) so you can see what a drag will do. Measure handle sizes in CSS pixels and convert with rect.width, so handles feel the same at any window size.

    The mirror again. If the box were stored in raw space, dragging right would have to decrease its x. Forget the sign and the box slides the opposite way from your mouse. Storing it in display space avoids the whole problem.

    In Dance

    The state machine reads the box every frame, so an edit takes effect on the next frame, about 33 ms later. Presets just replace the rectangle. The spec doesn't ask for the box to be remembered across reloads; per-session calibration is wish-listed for R6+.

    Tradeoff
    • The mouse is a setup tool: you're at the laptop when you edit the box and away from it while dancing. Precision matters less than "obvious and hard to break".
    • Larger handles are easier to grab but steal area from "move".
    You grab the box's left edge and drag it past the right edge, with no clamp. What happens to W, and what does the hit-test dx ≥ L && dx ≤ L + W do afterwards?Reveal

    W goes negative, so L + W is less than L. No number can be both ≥ L and ≤ L + W, and the box can never contain the hand. Gestures silently stop working, though the outline may still look plausible. A minimum-size clamp (or swapping edges when they cross) prevents it.

    R2 · Our geometry

    Measuring pinch and claw from landmarks

    Problem

    R4's knob needs a clutch: a way to say "I'm grabbing now". MediaPipe has no canned label for pinch or claw, so R2 measures them from the 21 points, and must keep GRABBED stable rather than flickering.

    Naive fix

    Pinch = "thumb tip within 30 px of index tip". At 1 m that might work. At 3 m the whole hand is about 30 px across, and everything reads as a pinch.

    Mechanism
    • Pinch (spec §5.2): dist(4, 8) / dist(0, 9), thumb tip to index tip divided by wrist to middle knuckle. That denominator is the same "palm size" R1's thumb rule already uses (src/pseudoChord.ts:57). Dividing makes the number independent of distance. Add hysteresis: grab below a low value, release only above a clearly higher one. The roadmap gives pinch a slider.
    • Claw (spec §5.2): a splayed hand whose four fingertips curl partway within about 0.5 s, "grabbing a ball". Curl per finger can be the same tip/PIP ratio R1 uses (config.ts:39; extended is about 1.3, curled under 1.0), with claw meaning all four sit in a middle band. The catch: a relaxed hand is naturally half curled. So claw is a temporal pattern: "was fully open within the last 0.5 s, and is now in the band". That is a small state machine of its own.
    • Two-hand (spec §5.2): one hand showing the canned Open_Palm is the modifier; while it's up, the other hand is the knob. The hands are told apart by screen side, never by label (see the live-test lesson above).
    • Tracking drops while grabbed: the value freezes, never jumps, and the clutch releases after about 0.3 s with no hand. That is another grace timer.
    In Dance

    R2 only shows GRABBED / released for each clutch; nothing is controlled until R4 (roadmap). Done means: grabs show correctly, or failures are noted. The wishlist's "can pinch and claw be read reliably farther away?" risk gets its first data here.

    Tradeoff
    • Pinch: simplest rule, but fingertips are small in the image, and when the thumb hides behind the index finger the model has to guess where the tips are. A fist can also bring the thumb tip close to the index finger; watch whether a fist reads as a pinch.
    • Claw: most natural feel, most tuning.
    • Two-hand: uses the most reliable shape, but needs both hands free.
    You step back from 1 m to 3 m. What happens to the thumb-to-index distance in pixels, to the pinch ratio, and to how much the ratio jitters?Reveal

    Pixel distance shrinks to roughly a third. The ratio stays about the same, because the denominator shrinks by the same factor. The jitter in the ratio grows: the model's error of a pixel or two is now a bigger share of a smaller hand. That is the reason pinch needs a dead band wider than you'd guess from testing up close.

    What R1 built on, now with pointers into the code on main. Each concept follows the same path: the problem, the naive fix and why it breaks, the actual mechanism, what Dance does with it, and what it costs.

    1 · The model

    How MediaPipe hand tracking works

    Problem

    Find the 21 joints of every hand in a camera frame, 30 times a second, on a laptop, inside a browser tab, without sending video anywhere.

    Naive fix

    Run one large neural network over the whole frame and ask it for every joint directly. That is slow, because the network has to look at every pixel at full size. It is also hard to train, because a hand can appear at any size, angle and position, with fingers in any arrangement.

    Mechanism

    Split the job into two easier models, and skip the first one most of the time.

    • Palm detector. Scans the whole frame for palms. Palms are rigid and roughly square, so they are far easier to find than a whole hand with floppy fingers. Output: a rotated box around each palm.
    • Landmark model. Cuts that box out, rotates it upright, and shrinks it to a small fixed size (about 224×224 pixels). On that tidy crop it predicts 21 points, a "hand is present" score, and a left/right guess.
    • Tracking. In video mode, the next frame's crop comes from this frame's 21 points, so the palm detector is skipped. It runs again only when the presence score drops below minTrackingConfidence (default 0.5), or when fewer hands are tracked than numHands asks for.
    • Gesture classifier. A third tiny model turns the 21 points into one of eight canned labels with a score: None, Closed_Fist, Open_Palm, Pointing_Up, Thumb_Down, Thumb_Up, Victory, ILoveYou.

    What one result contains (per detected hand h):

    FieldShapeMeaning
    landmarks[h][i]x, y, zx and y are fractions of the image width and height, 0 to 1 from the top-left. z is depth relative to the wrist, on roughly the same scale as x; more negative means closer to the camera. z is a rough estimate.
    worldLandmarks[h][i]x, y, z (metres)The same 21 points in real-world-ish 3D, centred on the hand. R1 doesn't use them.
    handedness[h][0]"Left" | "Right", scoreThe model's guess. MediaPipe's docs say it assumes a mirrored selfie image, so R1 first swapped it for our un-mirrored frames. The live test showed the unswapped label was already right (config.ts:66, see the lesson above).
    gestures[h][0]categoryName, scoreThe canned label, e.g. Victory at 0.91. R2's command shapes come from here.

    Landmark numbering. 0 is the wrist. Each finger then gets four points running from the base to the tip: thumb 1–4, index 5–8, middle 9–12, ring 13–16, pinky 17–20. On the four fingers the names are MCP (the big knuckle), PIP (middle joint), DIP (last joint) and TIP. The constants live in src/hand.ts:18–40.

    Why it runs every frame. Each frame is a new photo. The model remembers nothing between frames except the crop box from tracking. Video mode also needs a strictly increasing timestamp: main.ts:79–81 nudges it up by 1 ms if two frames land on the same performance.now().

    WASM. MediaPipe is written in C++, compiled to WebAssembly, a compact binary format the browser runs at close to native speed. FilesetResolver.forVisionTasks(path) fetches those files; R1 serves them from public/wasm, copied there by scripts/copy-wasm.mjs before dev and build. The model weights are a separate .task file, vendored at public/models/gesture_recognizer.task.

    GPU vs CPU delegate. The "delegate" decides where the neural-network maths runs. "GPU" turns it into WebGL shader programs, so thousands of multiply-adds run in parallel on the graphics chip. "CPU" runs it in WASM on the processor. GPU is usually faster per frame but pays a start-up cost and varies across machines. R1 tries GPU and falls back to CPU (recognizer.ts:29–34); the status bar shows which one won.

    In Dance

    One model only, in VIDEO mode with numHands: 2 (config.ts:54, used at recognizer.ts:26). The canned Open_Palm, Pointing_Up and Victory labels become the three command shapes. Pinch and claw have no label, so our own geometry handles them.

    Tradeoff
    • On-device: private, no network delay, works offline. In exchange you are limited by the laptop, and the first load downloads several MB.
    • Canned labels: free and robust, but fixed at eight. New shapes have to be geometry rules.
    • Tracking shortcut: fast while your hand stays in view. A hand that appears suddenly or moves very fast pays the full palm-detector cost again.
    R1 live test: "a bit choppy at startup until a hand appears", then smooth. Using the palm detector / tracking split, what's a plausible explanation?Reveal

    With no hand tracked, the expensive full-frame palm detector runs on every frame. GPU shaders may also still be compiling in the first seconds. Once a hand is found, tracking takes over and per-frame cost drops. With numHands: 2 and one hand up, the detector likely keeps searching for the second hand, so some extra cost remains. This is a hypothesis, not measured; it's on the wishlist as a minor "bug?".

    2 · Our geometry

    Pseudo-chords: is each finger up or down?

    Problem

    The canned label covers eight shapes. R1 also wanted a per-finger readout (T0 I1 M1 R0 P0) to debug with, and R2 needs pinch and claw. So we compute finger states ourselves from the 21 points.

    Naive fix

    "A finger is up if its tip is higher on screen than its middle joint": tip.y < pip.y. Tilt the hand sideways and "higher on screen" stops meaning "extended". Point a finger at the camera and the tip lands on top of the joint. And the thumb never moves up and down at all.

    Mechanism

    Use measurements that do not care about rotation or size.

    • Distance ratio. An extended finger's tip is far from the wrist; a curled one folds back toward it. Compare dist(wrist, tip) with dist(wrist, pip). Turning the hand doesn't change a distance, and dividing one distance by another cancels out how big the hand looks.
    • Joint angle. At a joint, the angle between the two bone vectors: straight is about 180°, folded is well under.
    • Equal units first. Raw landmarks are fractions of width and height, and a 1280×720 frame is wider than tall, so a "distance" in fractions is stretched. analyze.ts:26–28 converts to pixels on both axes (and scales z by the width) before any geometry.

    The thumb swings across the palm instead of curling toward it, so the ratio rule fails for it. R1's rule (pseudoChord.ts:56–69): the thumb is out when its tip is at least 0.5 palm sizes from the index knuckle and the angle at its IP joint is at least 125°.

    Palm facing uses a cross product of two knuckle vectors and needs the hand label. The live-test lesson above explains why.

    3 · The browser

    The camera pipeline: from sensor to overlay

    Problem

    Get live frames from the webcam, hand each new one to the model exactly once, and draw the skeleton exactly on top of a mirrored video.

    Naive fix

    Loop as fast as possible with requestAnimationFrame, run the model each time, and draw landmarks straight onto the canvas. You run the model twice on the same frame, and the skeleton appears on the wrong side of your mirrored body.

    Mechanism

    1. Open the camera. getUserMedia asks permission and resolves to a MediaStream. Browsers only allow this in a secure context: HTTPS or localhost. R1 asks for 1280×720 at 30 fps as "ideal" values, which the camera may lower (camera.ts:41–49), and turns each failure into a plain instruction (camera.ts:13–32).

    2. Show it. video.srcObject = stream; video.play(). The video element always holds the most recent frame; the model reads pixels from it.

    3. Pace the loop. requestAnimationFrame fires before every repaint (60 or 120 Hz) whether or not there's a new frame. requestVideoFrameCallback fires once per new video frame. R1 uses the second, falls back to the first (main.ts:103–109), and also skips a frame whose currentTime hasn't changed (main.ts:73–77).

    4. Mirror correctly. R1 picked the "flip both layers with CSS" option: #mirror holds the video and the canvas and is flipped with scaleX(-1) (style.css:87). draw.ts draws raw coordinates with no flipping, and the canvas's pixel grid is kept equal to the video's (main.ts:68–71) so dots don't drift off joints.

    5. fps is not latency. fps is how often you get an update. Latency is how old each update is. R1 averages fps over a 1 s window (main.ts:15–27). R3 will care about latency.

    Tradeoff
    • Model on the main thread: simple, but it blocks the page while it runs. That matters once audio and UI share the thread in R3. A Web Worker keeps the page responsive but means moving frames between threads.
    • 1280×720: sharper fingertips at a distance, more pixels to decode every frame. The landmark model works on a small crop anyway, so resolution mainly helps the palm detector find small, far hands. Detection still worked at 3–5 m in the live test.
    The camera delivers 30 fps and each model call takes 45 ms. What will the fps readout show? Does the skeleton fall further and further behind?Reveal

    About 22 fps (1000 / 45). Frames that arrive during a call are skipped: the video element only keeps the newest one. Nothing queues, so the skeleton never drifts further behind. Each update is at most one frame plus one inference old.

    4 · Tooling

    Vite, TypeScript, Vitest and npm scripts

    Mechanism
    • Vite serves .ts files on localhost, stripping types on the fly without checking them, and pushes code changes to the open tab (hot module replacement). vite build bundles everything into dist/.
    • TypeScript checks types before the code runs; then the types vanish. Because Vite never type-checks, the build runs tsc --noEmit first.
    • Vitest runs tests in Node with no browser and no camera. That works because the geometry is pure: give it 21 points, get a chord. Fixtures are hand-built hands in src/test/fixtures.ts.
    • npm scripts in package.json. predev and prebuild run automatically before dev and build, to copy the WASM files into public/.
    "dev": "vite" // local server + hot reload (predev copies WASM) "build": "tsc --noEmit && vite build" // type-check, then bundle to dist/ "test": "vitest run" // R1: 36 tests
    Tradeoff
    • Pure functions plus unit tests catch maths bugs cheaply. They can't catch a wrong assumption about the camera or the model, as the handedness flip showed. The live check covers that.
    With npm run dev running, you save a .ts file with a type error. Does the page break?Reveal

    Usually not. Vite strips types without checking, so the page reloads and runs. The error shows in your editor, in npm run typecheck, or when npm run build refuses to continue.

    5 · Preview, not in R2

    Later in R4–R5: rate vs position control

    Two mappings
    • Position control (the "absolute wiper"): the tilt angle is the value. Quick and exact for small ranges, but the whole range must fit one wrist sweep.
    • Rate control (the "spring-loaded joystick", the favourite): the angle sets how fast the value changes. Each frame does value += gain × (angle − centre) × dt. It never runs out of wrist. It also adds up jitter, so it needs a dead zone.

    Watch for dt (time since the last frame) in the R4 code. Without it, the knob would move faster on a faster laptop. R2's clutch shapes are the "grab" half of this knob.

    Glossary

    Terms you'll see in R2 diffs and reports, then the R1 terms.

    R2 terms

    finite state machine
    Code that is always in exactly one named state and moves between states only along defined transitions.
    transition / guard
    An allowed move between two states, and the condition that must be true for it to happen.
    step function
    The per-frame function that takes state, input and time and returns the next state plus any events.
    dwell
    How long a shape must be held before it counts. 0.6 s in R2.
    grace period
    How long a shape may vanish without counting as released. Forgives dropped frames.
    cooldown
    The time after a fire during which nothing else can fire. 1.0 s, plus a release.
    debounce
    Accept a change only after it has lasted a set time.
    hysteresis
    Separate on and off thresholds, so a value near the line doesn't flicker.
    dead band
    The gap between the on and off thresholds, where the output keeps its previous value.
    tap / hold
    Drop the shape after the inner ring fills (fires on release), or keep it up until the outer ring fills at about 1.5 s.
    armed
    Inner ring full, waiting to see whether this becomes a tap or a hold.
    command box
    The on-screen rectangle the palm centre must be inside for a shape to count.
    palm centre
    Average of landmarks 0, 5, 9, 13, 17 (wrist plus four knuckles).
    hit-test
    Deciding whether a point falls inside a shape, here a rectangle.
    display space / raw space
    Coordinates as you see them (mirrored) versus as the model outputs them (un-mirrored). x flips between them.
    pointer capture
    setPointerCapture: keep sending move events to one element during a drag, even off it.
    drag handle
    A small zone at an edge or corner that resizes instead of moving.
    clutch
    The "I'm grabbing now" signal for the knob: pinch, claw or two-hand.
    pinch ratio
    Thumb tip to index tip, divided by wrist to middle knuckle.
    false fire
    A command fired that you didn't intend. R2 logs them during a 2-minute dance.

    R1 terms

    landmark
    One of the 21 points on a hand the model outputs, 0 (wrist) to 20 (pinky tip).
    normalized coordinates
    Positions as fractions of the image size (0 to 1), not pixels.
    isotropic coordinates
    Same units on every axis (pixels here), so distances and angles aren't stretched. toIsotropic in analyze.ts.
    handedness
    The model's Left/Right guess per hand. On our frames it came out right unswapped.
    palm normal
    A vector sticking straight out of the palm, from a cross product of two knuckle vectors.
    cross product
    Two vectors in, one perpendicular vector out. On a flat image, the sign of its z says clockwise or counter-clockwise.
    MCP / PIP / DIP / TIP
    Knuckle, middle joint, last joint, fingertip. The thumb has CMC, MCP, IP and TIP.
    canned gesture
    One of the eight built-in labels, such as Victory.
    pseudo-chord
    Our five-digit finger readout, Thumb to Pinky, 1 = up. 01100 is a V.
    delegate (GPU / CPU)
    Where the model's maths runs: graphics chip through WebGL, or processor through WASM.
    WASM
    WebAssembly, a binary format browsers run at close to native speed.
    rVFC / rAF
    Run code once per new video frame / once per screen repaint.
    main thread
    The single thread for the page's JavaScript, layout and input. Long work here freezes the page.
    fps / latency
    Updates per second / how old each update is. Not the same thing.
    backing store
    A canvas's real pixel grid (canvas.width), separate from its CSS size.
    fixture
    Saved example input for a test, such as a hand-built set of 21 landmarks.
