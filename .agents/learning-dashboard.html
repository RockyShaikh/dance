R3: music under your hand

R2 ends with a FireEvent: { t, shape, kind }. R3 turns that into sound: load a local track, open palm plays and pauses, index up restarts from 0:00, with a big status word and a moving playhead. The hard part isn't calling play(). It's knowing what happens between that call and your ears, and what the browser does and doesn't allow. R3 is merged to main, so the pointers below are real files and lines.

Engine

An HTMLAudioElement, wrapped by src/audioPlayer.ts. Its header (L5–14) gives the reasons: decoding runs off the main thread, and preservesPitch covers R5.

One code path

Gestures, keys (Space, R, Home) and buttons all go through runTransport in src/transport.ts (L32–42). actionForFire (L13–22) maps open palm to toggle and index up to restart.

Measured

In the dev build, the element's audio event arrives 2–8 ms after the frame where the ring filled (recordTiming, main.ts:138–142). That's the command reaching the element, not yet the sound reaching your ears; see Latency below.

Browser rule

Chrome needs one click or key press before a gesture can start audio. R3 detects that and shows a hint (practice.ts:16, L101–104).

R3 · The browser's audio

Two ways to play a file: the audio element and Web Audio

Problem

An MP3 is compressed: a stream of small frames that must be decoded into raw samples (numbers between −1 and 1, 44,100 or 48,000 per second per channel) before a speaker can play them. Something has to read the file, decode it, keep the speaker fed without gaps, and let you pause and jump around.

Naive fix

Decode the whole file yourself in JavaScript and push samples to the speaker from the frame loop. The speaker needs a fresh chunk every few milliseconds. The frame loop runs every 33 ms and sometimes stalls for 40 ms inside the model. Every stall is an audible gap.

Mechanism

Browsers give you two finished answers. Both keep the speaker fed from a separate audio thread, so your code only sends commands.

  • Element: low memory, instant start on a long file, pitch-preserved speed for free. Loose control over timing: seeks take a moment, and section loops overshoot by however late your code notices the end.
  • Web Audio: exact timing, gapless loops, everything on one clock. Costs a decode wait on load (around a second for a song) and tens of MB of memory. Pitch-preserved speed needs a library.
Suppose R3 had used Web Audio. You pause at 1:12.4 by calling stop() on the source node. Later you call start() on that same node to resume. What happens, and what should the code do instead?Reveal

The browser throws an InvalidStateError: a buffer source node can only be started once. The code should create a new AudioBufferSourceNode on the same decoded buffer and call start(0, 72.4). Nodes are cheap; the 80 MB buffer is shared and never decoded again. So "pause" in Web Audio is really "stop, and remember where".

R3 · Timing

Audio latency: from "ring full" to sound in your ears

Problem

Roadmap R3's done means says "music reacts as soon as the ring completes, with no noticeable extra delay." To check that, you have to know where delay can come from, and turn "noticeable" into a number.

Naive view

"play() runs, sound comes out." In reality, the audio thread renders samples into a buffer slightly ahead of the speaker, and the device adds its own buffering on top. A sample written now is heard later, by an amount that depends mostly on the output device.

Mechanism

Split the time into what happens before the fire and what happens after it.

  1. Before the fire (deliberate). You hold the shape for the 0.6 s dwell. Each frame also arrives a camera frame late (about 33–50 ms) and spends one model call (10–40 ms) being read. The ring shows all of this, so it reads as "the system is confirming", not as lag.
  2. The fire. stepCommands returns a FireEvent on the frame where the ring fills. In the same JavaScript task, the R3 transport calls play() or start(). That step costs well under a millisecond.
  3. Audio thread. The audio thread works in chunks of 128 samples (a render quantum: 2.7 ms at 48 kHz). A start command takes effect at the next chunk.
  4. Output buffer. The browser keeps a few chunks queued so the speaker never runs dry. Web Audio reports this as ctx.baseLatency, typically a few to about 20 ms.
  5. Device. ctx.outputLatency is the operating system's estimate from there to the speaker. Built-in speakers and wired outputs add around 10–30 ms. A Bluetooth speaker compresses audio into packets and buffers them against radio dropouts, which typically adds 150–300 ms.
  6. Air. Sound travels 343 m/s: about 3 ms per metre.

What "noticeable" means. Your eyes see the ring complete after the next screen refresh and the display's own delay, roughly 20–40 ms after the fire. So the delay you feel is the gap between the ring filling on screen and the music starting. Broadcast standards (ITU-R BT.1359) put the point where people detect sound lagging the picture at around 125 ms. For a trigger like this, staying under about 50 ms feels instant. Wired output keeps the gap near zero. Bluetooth alone usually goes past 125 ms.

Making it measurable. Log timestamps per command, all on the performance.now() clock. R3 does the first part in dev builds: recordTiming (main.ts:138–142) stores the frame time when the ring filled, when the transport was called and when it returned, and every player event is time-stamped (main.ts:145–149). That's where the measured 2–8 ms comes from: frame to the element's play event. It stops at the element. Steps 4–6 (buffer, device, air) happen after it and aren't in that number. The browser can estimate them (AudioContext.outputLatency, which "Measure this device" in the lab reads), but only an outside check proves them: film the laptop with a phone in slow motion (240 fps = 4 ms per frame) and count frames between the ring filling and the sound in the video's audio track.

In Dance

The fire is handled before anything is logged or drawn (main.ts:105–111: "The music reacts on the very frame the ring completes"), and the transport call is synchronous, so steps 2–3 are as small as they can be. Spec §2: laptop or external speakers. The Bluetooth delay is still an Unresolved thread in the wish list. There's no way to make sound arrive earlier than the device allows. In R4 it matters a second way: you hear the music late, so you also mark late, by the device delay on top of your reaction time. The spec's 0.15 s late-mark offset (§4.6) could then subtract outputLatency as well.

Tradeoff
  • Smaller buffers mean lower latency but a higher risk of running dry (an underrun: a click or dropout) when the machine is busy. Web Audio's default latencyHint: "interactive" picks the smallest buffer the system can sustain.
  • Bluetooth trades latency for no cable. For drilling to music that's usually fine once it's playing; it's the start and the loop marks that feel late.

R3 · Timing

Seeking: how exactly can you land on a moment?

Problem

Restart means "jump to 0:00 and play". R4 will mean "jump to 1:31.20 and play", over and over. How precisely does a jump land, and how long does it take?

Naive view

"Time 91.2 s is just a position in the file." That's true only for uncompressed audio. In a compressed file, the browser has to work out where 91.2 s starts.

Mechanism
  • WAV is raw samples after a short header. The byte for time t is header + t × sampleRate × channels × bytesPerSample. The jump is exact and instant.
  • MP3 is a chain of frames of 1,152 samples each (26 ms at 44.1 kHz). In a constant-bitrate file every frame is the same size, so the arithmetic still works, to the frame. In a variable-bitrate file, frame sizes differ. The browser relies on a small table in the header (often only 100 entries, one per 1% of the song) or scans the file. Depending on the browser, a VBR seek can land slightly off.
  • Encoder delay. MP3 encoders put a few dozen milliseconds of silence at the very start. A restart to 0:00 includes it. Harmless for R3.
  • Decoded buffer (Web Audio). Once the track is decoded, time is an array index: 91.2 s × 48,000 = sample 4,377,600. Exact to a 48,000th of a second, with no decoding at seek time.
  • Seek time. An element seek is asynchronous: it finds the frame, refills the decoder and resumes. On a local file that's usually tens of milliseconds, and it adds directly to the "gap you feel". A buffer-source start costs nothing extra.
In Dance

R3 restarts with player.seek(0) then play() (transport.ts:39–40). seek clamps to the track and sets currentTime (audioPlayer.ts:160–165). 0:00 is exact in every format. Precision starts to matter in R4: the loop start is mid-song, you jump to it on every repeat, and "looping from end back to start is clean (no noticeable gap or overshoot)" is a done-means line.

Tradeoff
  • Decoding up front buys exact, instant seeks with a wait on load and tens of MB of memory.
  • Streaming buys a quick start with seeks that are fast enough for a restart but loose for tight loops.
Your track is a variable-bitrate MP3, played through the audio element as in R3. Is the R3 restart to 0:00 affected by VBR seeking? What about an R4 loop start at 1:31.20?Reveal

0:00 is always exact: it's the first frame, with no estimating needed. 1:31.20 is mid-file, so the browser has to locate it, and with a coarse table it may land a little off and take a moment. A decoded Web Audio buffer would land exactly on sample 4,377,600 (at 48 kHz) with no wait.

R3 · Browser rules

The autoplay policy: why the page needs one click first

Problem

Web pages that blast sound the moment they open are hostile, so browsers block audible playback until the person has actually interacted with the page. Dance wants to be hands-free. Where does that leave the first play?

Naive fix

Call play() when the first open-palm gesture fires. The ring fills, the banner shows, and there's silence. play()'s Promise rejects with NotAllowedError, or the AudioContext sits in the "suspended" state.

Mechanism
  • User activation. The browser keeps a per-page flag that only real input events set: a key press, a mouse button press, a tap. The events must be trusted: produced by the operating system, never by script. Once set, Chrome keeps this "sticky" activation for the life of the page.
  • The camera doesn't count. To the browser, a gesture Dance recognizes is just JavaScript calling play(), with no input event behind it. Neither does mouse movement, scrolling, or a drag-and-drop from Finder (the mouse press happened in Finder, not in the page).
  • Web Audio: a context created before any activation starts "suspended", and ctx.resume() works only after one. Element: play() returns a rejected Promise until then.
  • Chrome sometimes relaxes the rule for sites where you play a lot of media (the Media Engagement Index), so behaviour can differ between your profile and a fresh one. Don't rely on it.

In Dance

R3 handles it in two places. AudioPlayer.play() catches the rejection and turns NotAllowedError into a "blocked" event; AbortError (a pause arrived first) is ignored (audioPlayer.ts:126–139). Practice checks navigator.userActivation.hasBeenActive when a track loads (practice.ts:101–104) and shows "Click anywhere on the page once, so Chrome lets your hand start the music" (L16) until the first pointer or key press clears it (L67–73). Clicking "Open track" sets the activation itself; a drag-and-drop doesn't, which is exactly the case the hint covers. Non-Chrome wording is untested (wish list).

Tradeoff
  • One click per page load costs almost nothing, since you're at the laptop to pick the track anyway.
  • Failure mode: the gesture looks like it worked (ring, banner) but no sound plays. Without an on-screen message, it looks like an audio bug.
You open Dance, drag a track from Finder onto the page, step back to your spot and show an open palm in the box. You haven't clicked or pressed anything in the page. What happens?Reveal

The ring fills and the gesture fires, but there's no sound: a drop isn't an activation-triggering event, so play() rejects with NotAllowedError. In R3 you'd already have seen the hint, because hasBeenActive was false when the track loaded. The player emits "blocked", so the hint stays up. One click or key press anywhere fixes it for the rest of the session.

R3 · Threads

One main thread, two jobs: where stutter comes from

Problem

The roadmap warns: "watch for audio stutter while the hand model runs every frame." To know whether that's a real risk, you need to know which thread does what.

Naive view

"JavaScript is single-threaded, so while the model runs, the music must stop." That's half right. Your code runs on one thread, but the browser renders audio somewhere else.

Mechanism
  • The main thread runs one task at a time: your frame callback, input events, layout, painting. recognizeForVideo is synchronous (main.ts:265), so the page is busy for its whole duration, 10–40 ms per frame. Nothing else on the main thread runs in that time.
  • The audio thread is a separate high-priority thread that pulls samples from the already-decoded buffer or the element's decoder and hands them to the output buffer, chunk by chunk. It doesn't wait for the main thread. A track that is already playing keeps playing smoothly through a 40 ms model call, and even through a 300 ms freeze.
  • What does suffer is anything that needs the main thread at a precise moment:
    1. Commands land late. A key press during a model call waits for it to finish. A gesture fire is computed right after the call, so it doesn't wait twice.
    2. Loops timed from the main thread. "Check currentTime every frame; if past the loop end, seek back" overshoots by up to a frame plus a model call. With timeupdate it can be 250 ms. That's the R4 concern previewed below. Web Audio's loopEnd, or scheduling ahead on the audio clock with start(when), avoids it.
    3. Audio processing on the wrong thread. The old ScriptProcessorNode ran your sample code on the main thread, and glitched whenever the page was busy. Its replacement, AudioWorklet, runs on the audio thread, but must finish each 128-sample chunk in time (2.7 ms at 48 kHz) or the buffer runs dry and you hear a click. That's the R5 time-stretch risk.
    4. The whole machine is overloaded. Video decoding, the model on the GPU, and thermal throttling can, in bad cases, starve even the audio thread. Rare on a modern laptop.
  • Visual stutter is separate. The playhead and status word repaint only when the main thread is free. At 22 fps the playhead moves in steps, but the sound is still smooth.
In Dance

R3's play, pause and restart are one-off commands, so the main-thread cost is the measured 2–8 ms. The playhead is drawn the right way: Practice runs its own requestAnimationFrame loop (practice.ts:75–79) that reads player.currentTime, the audio element's own clock, on every repaint (render, L184–202), rather than counting frames. So a slow model call makes the playhead move in steps but never drift. If stutter shows up anyway, the bigger fix is moving the model into a Web Worker, so the main thread only paints and handles input.

Tradeoff
  • Model on the main thread: simple, and fine while the audio is a few commands. In a worker: frames have to be transferred between threads, and the code gets more complex.
  • Schedule ahead on the audio clock for anything rhythmic (loops, count-ins). React on the main thread for one-off commands.
The model call takes 40 ms per frame. A track is playing. Does the music stutter? What does get worse, and by how much?Reveal

The music doesn't stutter: the audio thread keeps pulling samples on its own. The fps drops to about 22, so the playhead moves in visible steps. A key press can land up to 40 ms late. And if R4 did loops by checking currentTime once per frame, each repeat could overshoot the loop end by up to about 45 ms (one frame interval plus the model call), audibly different on every pass.

Changing speed without chipmunks: pitch-preserving time-stretch

Problem

R5: turn the hand to slow the music down to 0.5× or speed it up to 1.25×, "pitch preserved" (roadmap R5, spec §9 Q3).

Naive fix

Play the samples faster or slower (resampling). Every frequency scales with the speed: 1.25× raises the pitch by 12 × log₂(1.25) ≈ 3.9 semitones; 0.5× drops it a full octave. That's the chipmunk effect, and it's what Web Audio's playbackRate does.

Mechanism
  • Grains. Cut the audio into short overlapping windows, around 20–50 ms. Read them from the input at one spacing and lay them down in the output at another. Spacing them out makes the music longer without changing the waveform inside each grain, so the pitch stays the same.
  • The catch: where two grains overlap, their waves may be out of step and partly cancel, which you hear as warble. WSOLA (waveform-similarity overlap-add) fixes that by sliding each new grain a few milliseconds to wherever it best lines up with what's already written, then crossfading. Chrome's audio element uses a WSOLA algorithm for playbackRate with preservesPitch.
  • Phase vocoder. The other family: take each grain into the frequency domain (FFT), keep the strength of each frequency, and adjust their phases to match the new spacing. Smooth on sustained notes, but drum hits get smeared. High-end stretchers such as Rubber Band combine both and treat drum hits specially.
In Dance

R3 picked the audio element partly for this (audioPlayer.ts:10–12), so R5 can set playbackRate and rely on preservesPitch. If R4 ever swaps in a Web Audio engine for tighter loops, R5 would need a stretcher library compiled to WebAssembly in an AudioWorklet (SoundTouch, Rubber Band), which brings back the "finish each chunk in 2.7 ms" risk from the threads section. That is the wish list's "live speed changes may clash with precise looping" thread. At the 1.0× detent, the element plays the file untouched.

Tradeoff
  • Artifacts grow with distance from 1.0×. At 0.5× each grain is used about twice, and drum hits can sound doubled.
  • Built-in stretch is free but its quality is fixed. A library is configurable but costs CPU on the audio thread, plus licence terms to check.
A song's main note is A at 440 Hz. At 0.8× with plain resampling, what frequency do you hear? With WSOLA, what frequency, and how long does a 3:00 song take?Reveal

Resampling: 440 × 0.8 = 352 Hz, about 3.9 semitones flat, and the song takes 3:45. WSOLA: still 440 Hz, and the song also takes 3:45. Both stretch time by 1 / 0.8 = 1.25; only WSOLA keeps the pitch.

R4a · Timing

Loop wrap: why a timer-based seek overshoots, and how look-ahead helps

Problem

Done means for R4: "Looping from end back to start is clean (no noticeable gap or overshoot), repeatedly." With the R3 audio element, nothing in the browser jumps back for you. Your code has to notice the playhead reached the loop end and seek to the start.

Naive fix

Listen for timeupdate and seek when currentTime ≥ loopEnd. Chrome fires timeupdate only about every 250 ms, so the music runs up to a quarter of a second past the end: an extra half-beat at 120 BPM, different on every pass.

Mechanism

Overshoot = how late the check notices + how long the seek takes. A check that runs once per frame notices up to one frame late: 33 ms at 30 fps, 67 ms if a dim room drops the camera to 15 fps. If the check shares the main thread with a 25 ms model call, it can be that much later again. Then the seek itself leaves a short gap while the element finds the new spot and refills its decoder.

Look-ahead moves the decision earlier. Each check asks "will the end arrive before my next check?" rather than "have I passed it?". If yes, it sets a one-shot timer for exactly the time left, (loopEnd − currentTime) / playbackRate. The timer usually fires within a millisecond or two of the end. Its limit is the main thread: if a model call is running when the timer is due, the timer waits for it.

Scheduling on the audio clock removes the main thread from the timing altogether. Web Audio does this with loopStart/loopEnd on a buffer source, or with start(when) on the audio clock, fed by a coarse JavaScript timer that only has to wake up before the deadline (the "two clocks" pattern). The audio element has no equivalent for seeks. That's the tradeoff the comment in audioPlayer.ts:13–14 names.

In Dance

R4a keeps the R3 audio element, so expect a per-frame check, ideally with look-ahead. Things to look for in the R4a code: where the check runs (the camera's frame callback, the practice view's requestAnimationFrame loop, or a timer), whether it divides by playbackRate (R5 will change it), and whether R4a logs the actual wrap time against loopEnd, like R3's recordTiming. If clean wraps can't be had by ear, the escape hatch is a Web Audio engine behind the same AudioPlayer interface.

Tradeoff
  • Element + look-ahead: keeps streaming and built-in pitch-preserved speed. Wraps are close but not sample-exact, and still have a seek gap.
  • Web Audio: exact, gapless wraps; costs the decode wait, memory, and a time-stretch library for R5.
  • Failure mode: a check that lives only in requestAnimationFrame stops when the window is hidden or minimized, and the music runs straight past the loop end.
R4a checks the loop end once per camera frame, with no look-ahead. The room gets dim and the camera drops to 15 fps. What happens to the worst-case overshoot? Would look-ahead still help?Reveal

Worst case doubles, from about 33 ms to about 67 ms past the end, plus the seek gap, and it varies from pass to pass, which the ear notices more than a constant offset. Look-ahead still helps: at the last check before the end, it sees "end in under 67 ms" and sets a timer for the exact remainder, so the frame rate stops mattering. Only a model call that happens to be running when the timer is due can delay it.

R4b · The knob

Rate vs position control: how turning becomes a value

Problem

R4b turns a hand tilt into a nudge of the loop start (R5 reuses it for speed). Your wrist tilts maybe 60–80° each way (spec §5.1). How should an angle map onto seconds so it's quick, precise, and never runs out of wrist?

Naive fix

Map the angle straight to the value: 1° = 0.1 s. Fine for a few seconds of nudge, but every pixel of landmark jitter moves the marker, and a bigger range needs a bigger sweep than the wrist has.

Mechanism

The tilt is the angle of the wrist → middle-knuckle needle from straight up (spec §5.3), atan2 of that vector. The clutch (claw by default, roadmap R4) says when the angle counts. Then one of four mappings (spec §5.4):

MappingEach frameRuns out?
Position (absolute wiper)value = f(angle)yes: the whole range must fit one sweep
Relative + ratchetvalue = v₀ + k·(angle − angle₀), from the grabre-grab to go further
Rate (spring-loaded joystick)value += gain·(angle − centre)·dt, zero inside a dead zonenever
Jog (circling)value += k·Δangle, unwrapped around ±180°never
  • dt is the clock lesson again. Without the time since the last frame, the joystick moves twice as fast at 60 fps as at 30. Same reason R2 times the dwell by clock, not by frames (commands.test.ts:436).
  • Rate control integrates. Small jitter in the angle adds up over time, so it needs a dead zone. You also react late: you hear "that's the spot" and release about 0.2 s later, so the value overshoots by rate × 0.2 s. That's why the spec keeps the nudge gain low and shows the start time huge while nudging (§5.5).
  • Position control passes jitter straight through, so it usually needs smoothing, which adds lag.
  • Unwrapping. atan2 jumps from +180° to −180°. Tilt never gets near that (the hand would point down), but circling crosses it on every lap: if one frame's change is over 180°, subtract 360°.
In Dance

R4b builds all four behind a settings switch, joystick tilt first. Claw is the default grab because the user found pinch rough (roadmap, 2026-10-12). Claw detection is R2's stepClaw (clutch.ts:85–99): it releases when the fingers leave the half-curled band, and a tracking drop holds the grab for 300 ms. Knob values should freeze, never jump, while tracking is lost (spec §5.2).

Tradeoff
  • Position: fast and direct, limited range, shows jitter.
  • Rate: unlimited range and steady, but slower to arrive and prone to overshoot. It needs a dead zone and low gain.
Joystick mapping with assumed numbers: dead zone 5°, gain 0.05 s per degree per second. You grab, tilt to 15° and hold for 2 s, then release. How far does the loop start move? What if the code forgot dt and added gain·(angle − centre) per frame at 30 fps?Reveal

Only the 10° beyond the dead zone counts: 10 × 0.05 × 2 = 1.0 s. Without dt it adds 10 × 0.05 = 0.5 s per frame, 60 frames in 2 s: 30 s. The marker would fly off, and twice as fast on a 60 fps camera.

What you saw

The fix

R2 as built: turning shapes into commands

R1 answers "what shape is this frame?" R2 answers "did the dancer deliberately make this shape, once, in the right place?" That second question is about history, time and space, not about one frame. Seven ideas make it work. R2 is merged to main (145 tests), so this section now points at the real code. Where the build differs from what v2 of this page predicted, the text says so.

Where the box lives

In display coordinates, as you see the mirrored picture (box.ts:4–9). The raw → display flip happens in exactly one place, palmCentre: x: 1 − mean (handFeatures.ts:16–25). The HUD is a second canvas that is not mirrored (hud.ts:4–8), so the box, rings and text are drawn straight in display coordinates.

Dwell timing

By the clock, not by counting frames. stepCommands takes the frame's performance.now() as t, and a test proves the ring fires at the same moment at 10, 30 and 120 fps (commands.test.ts:436–465).

Hand lost mid-gesture

Gone for over 120 ms (dropoutGraceMs) counts as released. Before the ring fills: nothing fires. After it fills (ARMED): it fires a TAP. After a hold already fired: nothing more. Coming back doesn't bank the earlier time (commands.ts:157–163; tests at commands.test.ts:467–500). Clutches hold for 300 ms, then release (clutch.ts:102–105).

Fist vs pinch

A fist has its thumb on the index too. A pinch can only start if the middle, ring and pinky reach out at least 1.3 (othersReach, clutch.ts:72; open ≈ 1.9, fist ≈ 1.0). Test: "a fist is not a pinch" (clutch.test.ts:225).

Claw vs relaxed hand

Told apart by the change: the hand must have been clearly open (reach ≥ 1.75) within 500 ms before it enters the half-curled band 1.25–1.65 (clutch.ts:85–99, config.ts:181). A hand that's just half-curled at rest never grabs (clutch.test.ts:269).

Which thresholds got hysteresis

Pinch: grab ≤ 0.30, release only ≥ 0.48 (× 1.6). Claw: the band widens by 0.08 each side once grabbed. Not the shape score (a single 0.5 floor; the 120 ms grace absorbs flicker) and not the box edge (edges count as inside, box.ts:42–44).

R2 · Gesture logic

Finite state machines: idle → dwell → armed → spent

Problem

Each frame, analyze() hands you a fresh reading with no memory of the last one. A command needs memory: how long has this shape been up, did it already fire, has the hand dropped since?

Naive fix

Put if (shape === "Open_Palm") togglePlay() in the frame loop. At 30 fps a one-second palm toggles play 30 times. The next naive fix is a handful of booleans (isHolding, hasFired, inCooldown, startedAt). Five booleans allow 32 combinations, most of which should be impossible, and bugs live in those combinations.

Mechanism

A finite state machine keeps the gesture in exactly one named state. Once per frame a step function looks at three things (the current state, this frame's input, the current time) and either stays put or follows one of a few allowed arrows. Side effects, such as firing a command or playing a sound, happen only on particular arrows.

// src/commands.ts:7–16, as built command shape · palm centre in box · palm facing · score ≥ 0.5 · only command hand · not cooling down IDLE ─────────────────────────────────────────────────────────────► DWELL since = t, inner ring fills ▲ │ gone > 120 ms ──► IDLE (nothing fires) │ │ t − since ≥ 600 ms │ ┌────────────────────────────┴──────────────┐ │ open palm: fire TAP now index / V: ARMED │ │ gone > 120 ms → fire TAP · t − since ≥ 1500 ms → fire HOLD │ ▼ │ └────────── shape gone > 120 ms ◄── SPENT ◄──────────────────────────────────────┘ every fire sets cooldownUntil = t + 1000 ms: no new DWELL may start before then
  • Time comes from timestamps, not frame counts. main.ts:261 computes ts = performance.now() once per frame, for both the model and the machine. "18 frames" is 0.6 s at 30 fps, but 1.2 s at 15 fps in a dim room.
  • "No hand" is an input. Frames keep arriving with an empty result when the hand leaves. The release rule at commands.ts:157–163 runs every frame, hand or not, so the machine can't get stuck in DWELL or ARMED.
  • "Fires exactly once" comes from SPENT, not from the cooldown. v2 of this page predicted a COOLDOWN state that needs both time and a release. The build splits the two jobs: SPENT waits for the release, and the cooldown is just a timestamp, cooldownUntil, that blocks a new DWELL from starting (commands.ts:149–152, L166). Fewer states, same behaviour.
  • Pure. stepCommands(prev, input, cfg) → { state, fired, view } (commands.ts:141) touches no camera and no DOM. The 500-line test file replays scripted timelines through it.
In Dance

The guards live in evaluateHands (commands.ts:123–133), checked in this order: command shape, palm centre in the box, only one such hand in the box, score ≥ 0.5, palm facing. The first one that fails becomes the "Not counting: …" message on the HUD. The optional stillness rule (off by default) restarts the dwell if the palm drifts more than 6% of the frame height (L174–183). since, when the ring started, pays off in R4, where loop marks are stamped at the ring's start minus 0.15 s (spec §4.6).

Tradeoff
  • Cost: more structure up front than a single if. Gain: every behaviour is an arrow you can point at, and impossible combinations can't happen.
  • Failure mode: a missing arrow becomes a stuck state, for example a lost hand that never returns the machine to IDLE. It shows up as "it stopped responding until I reloaded".

By then the cooldown is long over, so a new palm could start a dwell straight away. Test: "open palm held for 10 s fires exactly once" (commands.test.ts:126).

R2 · Gesture logic

Dwell: hold to confirm

Problem

Choreography passes through command shapes all the time: an arm sweep shows an open palm for a fraction of a second. The recognizer also misreads a frame here and there. Either one would fire a command by accident.

Naive fix

Fire on the first frame the shape appears. Every pass-through and every one-frame misread becomes a command.

Mechanism

Require the condition to hold continuously for a dwell time before acting. The ring is that requirement drawn on screen: progress = (now − t0) / 0.6 s.

  • Why it works on misreads. If a single frame is wrongly read as an open palm with probability p, and frames were independent, 18 wrong frames in a row (0.6 s at 30 fps) would have probability p18. With p = 0.1, that is 10−18. Real errors are correlated, so the real number is much higher, but the effect is still large.
  • Why it works on pass-throughs. A sweep shorter than 0.6 s never finishes the ring.
  • Where it does not help. A choreography pose that really is an open palm, held still in the box for a second, looks exactly like a command. Dwell filters short and flickery signals, not deliberate-looking ones. That is the spec's unresolved "choreography collides with commands" thread.
  • Grace period. One or two dropped frames in the middle of a real hold shouldn't reset the ring. A short grace (around 0.1 s) lets the shape vanish briefly without counting as lost. Too long, and two separate gestures merge into one.
In Dance

dwellMs: 600, slider range 0.6–1.2 s, saved with the box in localStorage (config.ts:107–120, settings.ts). The grace is dropoutGraceMs: 120, about 3–4 frames. The bench's "Start 2-minute test" button counts false fires while you dance (bench.ts), which is the data for tuning it.

Tradeoff
  • Latency on purpose: every command arrives at least 0.6 s after you make the shape. In R3 that dominates the delay budget by design. The ring makes the wait visible, so it feels deliberate rather than laggy.
  • Longer dwell: fewer false fires, slower commands. Shorter: the reverse.
An arm swing passes an open palm through the box for 0.3 s, five times in one phrase. Then, later, the choreography holds an open palm still in the box for 2 s. Dwell is 0.6 s. How many fires in total?Reveal

One. None of the 0.3 s passes completes the ring (the lab's "Dance move passes through" preset). The 2 s pose completes it at 0.6 s and fires, and cooldown blocks a second fire until the hand drops. Dwell can't tell a held pose from a command; the box, a longer dwell, or the stillness rule are the levers for that.

R2 · Gesture logic

Debouncing and hysteresis: why readouts flicker near a threshold

Problem

Every number the model gives you carries noise. When the true value sits near a threshold, noise pushes each frame randomly over or under it, so the readout flips at up to 30 times a second. R1's finger rule has a single threshold: extended when the tip/PIP distance ratio is at least 1.08 (src/config.ts:39, used at src/pseudoChord.ts:49). A half-bent finger sitting at 1.08 flickers.

Naive fix

Move the threshold. The flicker moves with it, to whichever hand pose now sits at the new line.

Mechanism

Two separate tools, working on two different axes.

  • Hysteresis works on the value axis. Use two thresholds: switch on above the high one, switch off below the low one, and in between keep whatever you were. A thermostat works this way (heat on at 19°, off at 21°). The gap, called a dead band, should be wider than the noise. Note what this costs: the output now depends on the previous output, so it is state, not a pure function of one frame.
  • Debouncing works on the time axis. Accept a change only after it has lasted a set time. The name comes from mechanical switches, whose contacts bounce for a few milliseconds. Dwell is a debounce on the "on" edge; the grace period is a debounce on the "off" edge.
  • Smoothing (an exponential moving average, avg = α·x + (1 − α)·avg) shrinks the noise but adds lag, and a smoothed value can still hover at a single threshold.

Distance makes all of this worse. Two metres back, your hand is a few dozen pixels tall and the model's pixel-level jitter is a bigger fraction of every ratio.

In Dance

As built, hysteresis is on the clutches only. Pinch grabs at ≤ 0.30 and releases at ≥ 0.30 × 1.6 = 0.48 (clutch.ts:73, config.ts:180). Claw enters the band 1.25–1.65 and stays until it leaves the band widened by 0.08 each side (clutch.ts:95). The shape score has a single 0.5 floor, and the box edge is a hard edge. For those, the 120 ms grace (a debounce on the off edge) does the flicker-fighting. If the real-hand test shows a ring that keeps restarting near the box edge or at a borderline score, those are the two places a dead band would go.

Tradeoff
  • Too narrow a dead band: flicker returns. Too wide: sticky. A pinch that is hard to release, or a readout that lags the truth.
  • Debounce always adds latency equal to its window.
Shape score hovers between 0.50 and 0.70. On-threshold 0.60, off-threshold 0.45. With hysteresis off (single line at 0.60), and then on, does the 0.6 s ring ever complete?Reveal

Off: the score keeps dipping under 0.60, and each dip longer than the grace period resets the ring, so it may never complete. On: once the score crosses 0.60, it only switches off below 0.45, which it never reaches, so the ring fills and fires. Check it with the "Flicker near threshold" preset and the Hysteresis button in the lab.

R2 · Gesture logic

Tap vs hold: deciding needs the future

Problem

Three shapes, more actions. Looper pedals double their vocabulary by giving each switch one action on a tap and another on a hold (spec §4.4).

Naive fix

Decide when the dwell ring fills. At that moment you can't know whether the dancer is about to drop the hand or keep holding.

Mechanism

Defer the decision with one extra state. When the inner ring fills, go to ARMED and wait.

ARMING ──(0.6 s)──► ARMED ──(released before 1.5 s)──► fire TAP → COOLDOWN └──(still held at 1.5 s)──► fire HOLD → COOLDOWN
  • Tap fires on release, so it lands later by however long you held past 0.6 s, plus the grace period that confirms the release.
  • Hold fires the moment the outer ring fills, without waiting for release.
  • A gesture with no hold action skips ARMED and fires as soon as the inner ring fills, which keeps play/pause fast.

A mouse does the same thing for single vs double click: it can't report "single" until the double-click window has passed.

In Dance

holdShapes: ["Pointing_Up", "Victory"] (config.ts:109); open palm has no hold, so it skips ARMED. Hold fires at max(1500, dwell + 400) ms (effectiveHoldMs, commands.ts:108–110), so a long dwell can't squash the tap window. R3 changed this for the practice view: PRACTICE.holdShapes is just ["Victory"] (config.ts:194–196, applied by practiceConfig in transport.ts:45–47), so index up restarts the moment the ring fills instead of on release. R4a must undo that to bring back index tap = loop start, hold = song start (wish list).

Tradeoff
  • Taps are slower than they look. The wishlist tracks this as "tap vs hold adds a short delay"; probably fine between attempts.
  • Lingering by accident turns a tap into a hold. The ring label (what will fire) is the defence.
Index up. The inner ring fills at 0.6 s; you keep holding until 1.2 s, then drop. Grace is 0.1 s. What fires, and when? And if you had dropped at 0.5 s?Reveal

On the R2 bench: TAP, at about 1.32 s (released at 1.2 s, plus the 120 ms grace). Dropping at 0.5 s fires nothing: the machine was still in DWELL, so losing the shape sends it back to IDLE. In R3's practice view, index has no hold, so it fires at 0.6 s whatever you do next.

    R2 · Input

    Mouse drag and resize handles

    Problem

    Click and drag inside the box to move it; drag an edge or corner to resize it; the new area takes effect immediately (roadmap R2 done means).

    Naive fix

    On mousemove with the button down, set box.x = mouse.x. The box's corner jumps to the cursor. Drag fast, the cursor leaves the element, events stop arriving, and the drag gets stuck. Adding each event's small movement to the box instead lets rounding errors pile up into drift.

    Mechanism

    A three-phase pointer protocol.

    1. pointerdown: decide what was grabbed. Hit-test zones in priority order: corner handles (within about 10 CSS px of a corner), then edges (within about 8 px), then inside (move), then outside (ignore). Save the mode, the pointer's start position, and a copy of the box as it was. Call el.setPointerCapture(e.pointerId) so every later move event comes to this element even when the cursor leaves it.
    2. pointermove: recompute from the start. dx = now − start, in display fractions. Move: L = L₀ + dx. Left edge: L = L₀ + dx, W = W₀ − dx. Right edge: W = W₀ + dx. Corners combine one horizontal and one vertical edge. Then clamp to 0…1 and to a minimum size. Always computing from the saved box, never from the last frame, is what stops drift.
    3. pointerup / pointercancel: finish. Clear the mode. Capture is released automatically.

    On hover, set the cursor to match the zone (move, ew-resize, ns-resize, nwse-resize, nesw-resize) so you can see what a drag will do. Measure handle sizes in CSS pixels and convert with rect.width, so handles feel the same at any window size.

    The mirror again. If the box were stored in raw space, dragging right would have to decrease its x. Forget the sign and the box slides the opposite way from your mouse. Storing it in display space avoids the whole problem.

    In Dance

    As built: hitTest (box.ts:59–73) grabs an edge within 14 CSS px on either side of it, and caps that zone at a third of the box so a small box still has a middle to move. applyDrag (L80–98) always works from the box as it was at pointerdown, and stops a dragged edge at the 8% minimum size. attachBoxEditor (boxEditor.ts:33–64) captures the pointer and calls setBox on every move, so an edit takes effect on the next frame. The box is also saved in localStorage, so it survives a reload (settings.ts:4), more than the spec asked for.

    Tradeoff
    • The mouse is a setup tool: you're at the laptop when you edit the box and away from it while dancing. Precision matters less than "obvious and hard to break".
    • Larger handles are easier to grab but steal area from "move".
    You grab the box's left edge and drag it past the right edge, with no clamp. What happens to W, and what does the hit-test dx ≥ L && dx ≤ L + W do afterwards?Reveal

    W goes negative, so L + W is less than L. No number can be both ≥ L and ≤ L + W, and the box can never contain the hand. Gestures silently stop working, though the outline may still look plausible. R2's clamp prevents it: the left edge stops at the right edge minus 0.08 (box.ts:93).

    Measuring pinch and claw from landmarks

    Problem

    R4's knob needs a clutch: a way to say "I'm grabbing now". MediaPipe has no canned label for pinch or claw, so R2 measures them from the 21 points, and must keep GRABBED stable rather than flickering.

    Naive fix

    Pinch = "thumb tip within 30 px of index tip". At 1 m that might work. At 3 m the whole hand is about 30 px across, and everything reads as a pinch.

    Mechanism
    • Pinch: pinchRatio = thumb tip to index tip ÷ wrist to middle knuckle (handFeatures.ts:36–40), so it doesn't depend on distance. Grab at ≤ 0.30 (slider 0.10–0.60), release at ≥ 0.48, and only start if the other three fingers reach out (the fist rule) and the palm is in the box (clutch.ts:66–77).
    • Claw: clawExtension = mean over index to pinky of (tip to wrist) ÷ (knuckle to wrist) (handFeatures.ts:55–57): open ≈ 1.9, claw 1.3–1.6, fist ≈ 1.0. The build uses this reach measure rather than R1's tip/PIP ratio. It's a temporal rule, as predicted: open (≥ 1.75) within the last 500 ms, now in the band (clutch.ts:85–99). It's the default grab for R4b.
    • Two-hand: the screen-left hand (as you see it) showing Open_Palm is the modifier, and the other hand must start in the box (clutch.ts:113–136). Hands are told apart by screen side, never by label (tested at clutch.test.ts:176).
    • Tracking drops while grabbed: the grab holds for releaseGraceMs: 300, then releases (clutch.ts:102–105). R4b's knob value should freeze during that time.
    In Dance

    R2 only shows GRABBED / released for each clutch, in the bench's clutch panel; nothing is controlled until R4b. One interaction to keep in mind: the two-hand modifier is an open palm, and an open palm in the box is also play/pause. With the default right-half box and the modifier on the left, they don't meet. With the whole-frame preset, a modifier palm held 0.6 s would toggle the music.

    Tradeoff
    • Pinch: simplest rule, but fingertips are small in the image, and when the thumb hides behind the index finger the model has to guess where the tips are. The user found it rough in practice, which is why R4b defaults to claw.
    • Claw: most natural feel, most tuning.
    • Two-hand: uses the most reliable shape, but needs both hands free.
    You step back from 1 m to 3 m. What happens to the thumb-to-index distance in pixels, to the pinch ratio, and to how much the ratio jitters?Reveal

    Pixel distance shrinks to roughly a third. The ratio stays about the same, because the denominator shrinks by the same factor. The jitter in the ratio grows: the model's error of a pixel or two is now a bigger share of a smaller hand. That is the reason pinch needs a dead band wider than you'd guess from testing up close.

    1 · The model

    How MediaPipe hand tracking works

    Problem

    Find the 21 joints of every hand in a camera frame, 30 times a second, on a laptop, inside a browser tab, without sending video anywhere.

    Naive fix

    Run one large neural network over the whole frame and ask it for every joint directly. That is slow, because the network has to look at every pixel at full size. It is also hard to train, because a hand can appear at any size, angle and position, with fingers in any arrangement.

    Mechanism

    Split the job into two easier models, and skip the first one most of the time.

    • Palm detector. Scans the whole frame for palms. Palms are rigid and roughly square, so they are far easier to find than a whole hand with floppy fingers. Output: a rotated box around each palm.
    • Landmark model. Cuts that box out, rotates it upright, and shrinks it to a small fixed size (about 224×224 pixels). On that tidy crop it predicts 21 points, a "hand is present" score, and a left/right guess.
    • Tracking. In video mode, the next frame's crop comes from this frame's 21 points, so the palm detector is skipped. It runs again only when the presence score drops below minTrackingConfidence (default 0.5), or when fewer hands are tracked than numHands asks for.
    • Gesture classifier. A third tiny model turns the 21 points into one of eight canned labels with a score: None, Closed_Fist, Open_Palm, Pointing_Up, Thumb_Down, Thumb_Up, Victory, ILoveYou.

    What one result contains (per detected hand h):

    FieldShapeMeaning
    landmarks[h][i]x, y, zx and y are fractions of the image width and height, 0 to 1 from the top-left. z is depth relative to the wrist, on roughly the same scale as x; more negative means closer to the camera. z is a rough estimate.
    worldLandmarks[h][i]x, y, z (metres)The same 21 points in real-world-ish 3D, centred on the hand. R1 doesn't use them.
    handedness[h][0]"Left" | "Right", scoreThe model's guess. MediaPipe's docs say it assumes a mirrored selfie image, so R1 first swapped it for our un-mirrored frames. The live test showed the unswapped label was already right (config.ts:66, see the lesson above).
    gestures[h][0]categoryName, scoreThe canned label, e.g. Victory at 0.91. R2's command shapes come from here.

    Landmark numbering. 0 is the wrist. Each finger then gets four points running from the base to the tip: thumb 1–4, index 5–8, middle 9–12, ring 13–16, pinky 17–20. On the four fingers the names are MCP (the big knuckle), PIP (middle joint), DIP (last joint) and TIP. The constants live in src/hand.ts:18–40.

    Why it runs every frame. Each frame is a new photo. The model remembers nothing between frames except the crop box from tracking. Video mode also needs a strictly increasing timestamp: main.ts:261–263 nudges it up by 1 ms if two frames land on the same performance.now().

    WASM. MediaPipe is written in C++, compiled to WebAssembly, a compact binary format the browser runs at close to native speed. FilesetResolver.forVisionTasks(path) fetches those files; R1 serves them from public/wasm, copied there by scripts/copy-wasm.mjs before dev and build. The model weights are a separate .task file, vendored at public/models/gesture_recognizer.task.

    GPU vs CPU delegate. The "delegate" decides where the neural-network maths runs. "GPU" turns it into WebGL shader programs, so thousands of multiply-adds run in parallel on the graphics chip. "CPU" runs it in WASM on the processor. GPU is usually faster per frame but pays a start-up cost and varies across machines. R1 tries GPU and falls back to CPU (recognizer.ts:29–34); the status bar shows which one won.

    In Dance

    One model only, in VIDEO mode with numHands: 2 (config.ts:54, used at recognizer.ts:26). The canned Open_Palm, Pointing_Up and Victory labels become the three command shapes. Pinch and claw have no label, so our own geometry handles them.

    Tradeoff
    • On-device: private, no network delay, works offline. In exchange you are limited by the laptop, and the first load downloads several MB.
    • Canned labels: free and robust, but fixed at eight. New shapes have to be geometry rules.
    • Tracking shortcut: fast while your hand stays in view. A hand that appears suddenly or moves very fast pays the full palm-detector cost again.
    R1 live test: "a bit choppy at startup until a hand appears", then smooth. Using the palm detector / tracking split, what's a plausible explanation?Reveal

    With no hand tracked, the expensive full-frame palm detector runs on every frame. GPU shaders may also still be compiling in the first seconds. Once a hand is found, tracking takes over and per-frame cost drops. With numHands: 2 and one hand up, the detector likely keeps searching for the second hand, so some extra cost remains. This is a hypothesis, not measured; it's on the wishlist as a minor "bug?".

    2 · Our geometry

    Pseudo-chords: is each finger up or down?

    Problem

    The canned label covers eight shapes. R1 also wanted a per-finger readout (T0 I1 M1 R0 P0) to debug with, and R2 needs pinch and claw. So we compute finger states ourselves from the 21 points.

    Naive fix

    "A finger is up if its tip is higher on screen than its middle joint": tip.y < pip.y. Tilt the hand sideways and "higher on screen" stops meaning "extended". Point a finger at the camera and the tip lands on top of the joint. And the thumb never moves up and down at all.

    Mechanism

    Use measurements that do not care about rotation or size.

    • Distance ratio. An extended finger's tip is far from the wrist; a curled one folds back toward it. Compare dist(wrist, tip) with dist(wrist, pip). Turning the hand doesn't change a distance, and dividing one distance by another cancels out how big the hand looks.
    • Joint angle. At a joint, the angle between the two bone vectors: straight is about 180°, folded is well under.
    • Equal units first. Raw landmarks are fractions of width and height, and a 1280×720 frame is wider than tall, so a "distance" in fractions is stretched. analyze.ts:36–38 converts to pixels on both axes (and scales z by the width) before any geometry.

    The thumb swings across the palm instead of curling toward it, so the ratio rule fails for it. R1's rule (pseudoChord.ts:56–69): the thumb is out when its tip is at least 0.5 palm sizes from the index knuckle and the angle at its IP joint is at least 125°.

    Palm facing uses a cross product of two knuckle vectors and needs the hand label. The live-test lesson above explains why.

    • Ratio: simple and fast. R1 includes the model's rough z in its distances, which may help a finger pointed at the camera; untested.
    • Any threshold trades missed shapes against false ones. You tune it by watching the readout, which is why R1 shows it.

Since z is the noisiest output, expect it to help only partly.

    3 · The browser

    The camera pipeline: from sensor to overlay

    Problem

    Get live frames from the webcam, hand each new one to the model exactly once, and draw the skeleton exactly on top of a mirrored video.

    Naive fix

    Loop as fast as possible with requestAnimationFrame, run the model each time, and draw landmarks straight onto the canvas. You run the model twice on the same frame, and the skeleton appears on the wrong side of your mirrored body.

    Mechanism

    1. Open the camera. getUserMedia asks permission and resolves to a MediaStream. Browsers only allow this in a secure context: HTTPS or localhost. R1 asks for 1280×720 at 30 fps as "ideal" values, which the camera may lower (camera.ts:41–49), and turns each failure into a plain instruction (camera.ts:13–32).

    2. Show it. video.srcObject = stream; video.play(). The video element always holds the most recent frame; the model reads pixels from it.

    3. Pace the loop. requestAnimationFrame fires before every repaint (60 or 120 Hz) whether or not there's a new frame. requestVideoFrameCallback fires once per new video frame. R1 uses the second, falls back to the first (main.ts:282–288), and also skips a frame whose currentTime hasn't changed (main.ts:254–259).

    4. Mirror correctly. R1 picked the "flip both layers with CSS" option: #mirror holds the video and the canvas and is flipped with scaleX(-1) (style.css:109). draw.ts draws raw coordinates with no flipping, and the canvas's pixel grid is kept equal to the video's (main.ts:86–93) so dots don't drift off joints.

    5. fps is not latency. fps is how often you get an update. Latency is how old each update is. R1 averages fps over a 1 s window (main.ts:27–39). R3 cares about latency; see the R3 section.

    Tradeoff
    • Model on the main thread: simple, but it blocks the page while it runs. R3 shows why that doesn't stutter the music (the audio thread is separate). A Web Worker keeps the page responsive but means moving frames between threads.
    • 1280×720: sharper fingertips at a distance, more pixels to decode every frame. The landmark model works on a small crop anyway, so resolution mainly helps the palm detector find small, far hands. Detection still worked at 3–5 m in the live test.
    The camera delivers 30 fps and each model call takes 45 ms. What will the fps readout show? Does the skeleton fall further and further behind?Reveal

    About 22 fps (1000 / 45). Frames that arrive during a call are skipped: the video element only keeps the newest one. Nothing queues, so the skeleton never drifts further behind. Each update is at most one frame plus one inference old.

    4 · Tooling

    Vite, TypeScript, Vitest and npm scripts

    Mechanism
    • Vite serves .ts files on localhost, stripping types on the fly without checking them, and pushes code changes to the open tab (hot module replacement). vite build bundles everything into dist/.
    • TypeScript checks types before the code runs; then the types vanish. Because Vite never type-checks, the build runs tsc --noEmit first.
    • Vitest runs tests in Node with no browser and no camera. That works because the geometry is pure: give it 21 points, get a chord. Fixtures are hand-built hands in src/test/fixtures.ts.
    • npm scripts in package.json. predev and prebuild run automatically before dev and build, to copy the WASM files into public/.
    "dev": "vite" // local server + hot reload (predev copies WASM) "build": "tsc --noEmit && vite build" // type-check, then bundle to dist/ "test": "vitest run" // R1: 36 tests
    Tradeoff
    • Pure functions plus unit tests catch maths bugs cheaply. They can't catch a wrong assumption about the camera or the model, as the handedness flip showed. The live check covers that.
    With npm run dev running, you save a .ts file with a type error. Does the page break?Reveal

    Usually not. Vite strips types without checking, so the page reloads and runs. The error shows in your editor, in npm run typecheck, or when npm run build refuses to continue.

    Glossary

    Terms you'll see in R3 and R4 diffs and reports, then R2, then R1.

    R3 and R4 terms

    HTMLAudioElement
    The browser's built-in player behind <audio>. Streams and decodes a file for you. R3's engine.
    Web Audio API
    A graph of audio nodes on an AudioContext, with its own clock. Precise timing; you manage decoding and playback yourself.
    AudioBuffer / buffer source
    A fully decoded track in memory, and the single-use node that plays it.
    object URL
    blob: URL from URL.createObjectURL(file), letting the audio element read a local file. Freed with revokeObjectURL.
    transport
    The play / pause / restart controls. In Dance, runTransport, shared by gestures, keys and buttons.
    audio thread
    A separate high-priority thread that feeds samples to the speaker. Not blocked by the hand model.
    render quantum
    The 128-sample chunk the audio thread works in: 2.7 ms at 48 kHz.
    output latency
    Time from a sample leaving the browser to the speaker. Small when wired, roughly 150–300 ms over Bluetooth.
    underrun
    The output buffer ran dry because audio work was late. Heard as a click or dropout.
    seek / seek gap
    Jumping the playhead (currentTime = t), and the short silence while the element finds the new spot.
    CBR / VBR
    Constant or variable bitrate MP3. Seeking in VBR needs a table or a scan.
    user activation
    The browser's record that a real click or key press happened on the page. Needed before audible playback.
    autoplay policy
    The rule that blocks sound until user activation. play() rejects with NotAllowedError.
    overshoot (loop)
    Music played past the loop end before the jump back. How late the check noticed, plus the seek.
    look-ahead
    Checking whether a deadline falls before the next check, and scheduling it exactly instead of noticing it late.
    rate / position control
    The tilt sets how fast the value changes (joystick), or the tilt is the value (wiper).
    dead zone
    A small range around centre where the joystick does nothing, so jitter doesn't drift the value.
    time-stretch / WSOLA
    Changing speed without changing pitch, by overlapping short grains; WSOLA aligns each grain to the waveform first.
    preservesPitch
    Audio element flag, on by default: playbackRate changes speed, not pitch.

    R2 terms

    finite state machine
    Code that is always in exactly one named state and moves between states only along defined transitions.
    transition / guard
    An allowed move between two states, and the condition that must be true for it to happen.
    step function
    The per-frame function that takes state, input and time and returns the next state plus any events.
    dwell
    How long a shape must be held before it counts (0.6 s), and the code's name for the state while the inner ring fills.
    grace period
    How long a shape may vanish without counting as released. Forgives dropped frames.
    cooldown / spent
    After a fire, no new dwell may start for 1.0 s (cooldownUntil). SPENT is the state that waits for the hand to drop.
    debounce
    Accept a change only after it has lasted a set time.
    hysteresis
    Separate on and off thresholds, so a value near the line doesn't flicker.
    dead band
    The gap between the on and off thresholds, where the output keeps its previous value.
    tap / hold
    Drop the shape after the inner ring fills (fires on release), or keep it up until the outer ring fills at about 1.5 s.
    armed
    Inner ring full, waiting to see whether this becomes a tap or a hold.
    command box
    The on-screen rectangle the palm centre must be inside for a shape to count.
    palm centre
    Average of landmarks 0, 5, 9, 13, 17 (wrist plus four knuckles).
    hit-test
    Deciding whether a point falls inside a shape, here a rectangle.
    display space / raw space
    Coordinates as you see them (mirrored) versus as the model outputs them (un-mirrored). x flips between them.
    pointer capture
    setPointerCapture: keep sending move events to one element during a drag, even off it.
    drag handle
    A small zone at an edge or corner that resizes instead of moving.
    clutch
    The "I'm grabbing now" signal for the knob: pinch, claw or two-hand.
    pinch ratio
    Thumb tip to index tip, divided by wrist to middle knuckle. Grab ≤ 0.30, release ≥ 0.48.
    finger reach (clawExt)
    Fingertip-to-wrist ÷ knuckle-to-wrist, averaged. Open ≈ 1.9, claw 1.3–1.6, fist ≈ 1.0.
    false fire
    A command fired that you didn't intend. R2 logs them during a 2-minute dance.

    R1 terms

    landmark
    One of the 21 points on a hand the model outputs, 0 (wrist) to 20 (pinky tip).
    normalized coordinates
    Positions as fractions of the image size (0 to 1), not pixels.
    isotropic coordinates
    Same units on every axis (pixels here), so distances and angles aren't stretched. toIsotropic in analyze.ts.
    handedness
    The model's Left/Right guess per hand. On our frames it came out right unswapped.
    palm normal
    A vector sticking straight out of the palm, from a cross product of two knuckle vectors.
    cross product
    Two vectors in, one perpendicular vector out. On a flat image, the sign of its z says clockwise or counter-clockwise.
    MCP / PIP / DIP / TIP
    Knuckle, middle joint, last joint, fingertip. The thumb has CMC, MCP, IP and TIP.
    canned gesture
    One of the eight built-in labels, such as Victory.
    pseudo-chord
    Our five-digit finger readout, Thumb to Pinky, 1 = up. 01100 is a V.
    delegate (GPU / CPU)
    Where the model's maths runs: graphics chip through WebGL, or processor through WASM.
    WASM
    WebAssembly, a binary format browsers run at close to native speed.
    rVFC / rAF
    Run code once per new video frame / once per screen repaint.
    main thread
    The single thread for the page's JavaScript, layout and input. Long work here freezes the page.
    fps / latency
    Updates per second / how old each update is. Not the same thing.
    backing store
    A canvas's real pixel grid (canvas.width), separate from its CSS size.
    fixture
    Saved example input for a test, such as a hand-built set of 21 landmarks.
