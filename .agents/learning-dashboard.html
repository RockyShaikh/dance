How the webcam reads your hand T0 I1 M1 R0 P0

R1 opens the laptop camera, finds your hands, draws their skeleton, and prints which fingers are up. This page explains what happens underneath each of those steps, so you can judge the code when it lands.

How the pieces connect

One trip around this loop happens for every camera frame, about 30 times a second. Colour tells you who owns each step: the browser, the MediaPipe model, or code the R1 branch writes.

1 · The model

How MediaPipe hand tracking works

Problem

Find the 21 joints of every hand in a 640×480 image, 30 times a second, on a laptop, inside a browser tab, without sending video anywhere.

Naive fix

Run one large neural network over the whole frame and ask it for every joint directly. That is slow, because the network has to look at every pixel at full size. It is also hard to train, because a hand can appear at any size, angle and position, with fingers in any arrangement.

Mechanism

Split the job into two easier models, and skip the first one most of the time.

  • Palm detector. Scans the whole frame for palms. Palms are rigid and roughly square, so they are far easier to find than a whole hand with floppy fingers. Output: a rotated box around each palm.
  • Landmark model. Cuts that box out, rotates it upright, and shrinks it to a small fixed size (about 224×224 pixels). On that tidy crop it predicts 21 points, a "hand is present" score, and a left/right guess.
  • Tracking. In video mode, the next frame's crop comes from this frame's 21 points, so the palm detector is skipped. It runs again only when the presence score drops below minTrackingConfidence (default 0.5), or when fewer hands are tracked than numHands asks for.
  • Gesture classifier. The Gesture Recognizer adds a third tiny model that turns the 21 points into one of eight canned labels with a score: None, Closed_Fist, Open_Palm, Pointing_Up, Thumb_Down, Thumb_Up, Victory, ILoveYou.

What one result contains (per detected hand h):

FieldShapeMeaning
landmarks[h][i]x, y, zx and y are fractions of the image width and height, 0 to 1 from the top-left. z is depth relative to the wrist, on roughly the same scale as x; more negative means closer to the camera. z is a rough estimate.
worldLandmarks[h][i]x, y, z (metres)The same 21 points in real-world-ish 3D, centred on the hand. They do not change when you step back from the camera, which makes them good for angles.
handedness[h][0]"Left" | "Right", scoreThe model's guess, which assumes a mirrored selfie image. Browser camera frames are not mirrored (the mirror is only CSS), so the label can come out swapped. The spec tells hands apart by screen side for this reason.
gestures[h][0]categoryName, scoreThe canned label, e.g. Victory at 0.91.

Landmark numbering. 0 is the wrist. Each finger then gets four points running from the base to the tip: thumb 1–4, index 5–8, middle 9–12, ring 13–16, pinky 17–20. On the four fingers the names are MCP (the big knuckle), PIP (middle joint), DIP (last joint) and TIP. So index tip = 8, and middle knuckle = 9. The lab in the next section labels all 21.

Why it runs every frame. Each frame is a new photo. The model remembers nothing between frames except the crop box from tracking, so if you stop calling it, the skeleton stops. Video mode also needs a timestamp that increases on every call: recognizeForVideo(video, performance.now()).

WASM. MediaPipe is written in C++. It is compiled to WebAssembly, a compact binary format the browser runs at close to native speed. FilesetResolver.forVisionTasks(path) fetches those .wasm files. The package ships a SIMD build and a nosimd fallback for older CPUs. The model weights are a separate .task file, a bundle of the three models, also fetched over HTTP when the page starts.

GPU vs CPU delegate. The "delegate" decides where the neural-network maths runs. "GPU" turns it into WebGL shader programs, so thousands of multiply-adds run in parallel on the graphics chip. "CPU" runs it in WASM on the processor. GPU is usually faster per frame, but it pays a start-up cost (shaders compile on the first frames) and behaves differently across machines and drivers. CPU is slower but predictable.

In Dance

R1 uses the Gesture Recognizer as the only vision model (spec §6.1). The canned Open_Palm, Pointing_Up and Victory labels become the three command shapes in R2–R4, because a trained classifier beats hand-written rules for those. Pinch and claw have no canned label, so our own geometry handles them (next section). Set numHands: 2: the default is 1, and the spec says either hand can command.

Tradeoff
  • On-device: private, no network delay, works offline. In exchange you are limited by the laptop, and the first load downloads several MB of WASM and model.
  • Canned labels: free and robust. In exchange the set is fixed at eight. Adding a ninth means training a new classifier, which the spec rules out, so new shapes are geometry rules.
  • Tracking shortcut: fast while your hand stays in view. In exchange, a hand that appears suddenly or moves very fast can lose tracking and pay the full palm-detector cost again, which you see as a stutter.
You set numHands: 2 and hold up one hand. Does the palm detector still run on every frame? What would you expect to see on the fps readout compared with numHands: 1?Reveal

Very likely yes. Tracking only follows hands the model already has. With one of two slots empty, it keeps running the palm detector to look for the second hand, so the cheap tracking path never fully kicks in. Expect somewhat lower fps with one hand at numHands: 2 than at numHands: 1.

This is cheap to verify in R1: note fps at each setting with one hand up. If the gap is large, that is a design input for R2 (for example, "one hand at a time" is already a spec rule).

2 · Our geometry

Pseudo-chords: is each finger up or down?

Problem

The canned label covers eight shapes. R1 also wants a per-finger readout (T0 I1 M1 R0 P0) to debug with, and R2 needs pinch and claw, which no label covers. So we compute finger states ourselves from the 21 points.

Naive fix

"A finger is up if its tip is higher on screen than its middle joint": tip.y < pip.y. It works for an upright hand facing the camera. Tilt the hand sideways and "higher on screen" stops meaning "extended". Point a finger at the camera and the tip lands on top of the joint. And the thumb never moves up and down at all.

Mechanism

Use measurements that do not care about rotation or size. There are two common families.

  • Distance ratio. An extended finger's tip is far from the wrist; a curled one folds back toward it. Compare dist(wrist, tip) with dist(wrist, pip). Turning the hand doesn't change a distance, and dividing one distance by another cancels out how big the hand looks. Cheap, works on 2D points.
  • Joint angle. At the PIP joint, take the vector to the knuckle and the vector to the tip. Straight finger: about 180°. Curled: well under that. Compute it on worldLandmarks (3D, metres), so a finger pointing at the camera still measures as straight.
  • Hysteresis. Use two thresholds: a finger must cross a high line to become "up" and fall below a lower line to become "down". A value hovering near a single line then doesn't flicker.

Why the thumb is the hard one. It has different joints (1 CMC, 2 MCP, 3 IP, 4 tip) and moves in a different plane: it swings across the palm instead of curling toward it. A folded thumb's tip stays about as far from the wrist as an open one, so the ratio rule fails. Usual fixes: measure the thumb tip's distance to the pinky knuckle (17) divided by palm width (5 to 17), or use thumb joint angles. Which side the thumb sits on also flips with left vs right hand and palm facing toward vs away.

Palm facing comes from the same toolbox. Take the cross product of wrist→index knuckle and wrist→pinky knuckle. The sign of its z component says whether the palm or the back of the hand faces the camera, and that sign flips for the other hand.

Why tolerance matters at dance distance. Step back two metres and your hand shrinks to perhaps 50 pixels tall. The model's jitter of a pixel or two is now a big fraction of the hand. Any threshold written in pixels, or in image fractions, changes meaning as you move. Ratios inside the hand don't. Values near a threshold will still flicker more at a distance, which is the job of R2's hold-to-confirm.

In Dance

The R1 readout shows the chord next to MediaPipe's label (roadmap R1 "done means": curling each finger flips its readout correctly). In R2 the same feature code adds pinch distance and claw curl, both measured relative to hand size (spec §5.2). Tradeoff
  • Ratio: simple and fast, but 2D, so it can misread fingers pointing at the camera.
  • Angle on world landmarks: handles depth, but it leans on the model's z estimate, its noisiest output.
  • Any threshold trades missed shapes against false ones. You tune it by watching the readout, which is exactly why R1 shows it.
Point your index finger straight at the camera, like aiming at it. What will rule C say, and which approach from above would read it correctly?Reveal

In the 2D image the tip lands almost on top of the PIP joint, so dist(wrist, tip) is about the same as dist(wrist, pip). The ratio sits near 1.0 and the finger reads as down, or flickers.

The joint angle computed on worldLandmarks sees a straight finger (about 180°), because those points have real depth. This is a likely surprise in R1 testing, worth noting if it happens.

3 · The browser

The camera pipeline: from sensor to overlay

Problem

Get live frames from the webcam, hand each new one to the model exactly once, and draw the skeleton exactly on top of a mirrored video.

Naive fix

Loop as fast as possible with setInterval or requestAnimationFrame, run the model each time, and draw the landmark coordinates straight onto the canvas. You end up running the model twice on the same frame, and the skeleton appears on the wrong side of your mirrored body.

Mechanism

1. Open the camera. navigator.mediaDevices.getUserMedia({ video: { width: 640, height: 480, facingMode: "user" } }) asks permission and resolves to a MediaStream, a live handle on the camera. Browsers only allow this in a secure context: HTTPS, or localhost. That's why the Vite dev server on localhost works, while opening the same page from another device over plain http://192.168… would be refused.

2. Show it. video.srcObject = stream; video.play(). The video element decodes the stream and always holds the most recent frame. The model reads pixels straight from that element; on the GPU path they are uploaded as a texture.

3. Pace the loop.

  • requestAnimationFrame(cb) fires before every screen repaint: 60 or 120 times a second, whether or not the camera produced a new frame. With a 30 fps camera, half the calls see a frame you already processed.
  • video.requestVideoFrameCallback(cb) fires once per new video frame and passes metadata (mediaTime, presentedFrames). No duplicate work. It's a one-shot, so the callback registers itself again at the end. Supported in Chrome, the spec's target.

4. Mirror correctly. People expect a selfie view, but camera pixels and landmarks are not mirrored. Pick one of two consistent options:

// Option A: flip both layers with CSS, draw raw coordinates video, canvas { transform: scaleX(-1); } px = lm.x * canvas.width; py = lm.y * canvas.height; // Option B: show the video flipped, flip the maths when drawing px = (1 - lm.x) * canvas.width; py = lm.y * canvas.height;

Mixing them (flipped video, unflipped drawing) puts your right hand's skeleton over your left hand. With option A, any text drawn into the canvas also comes out backwards, so readouts belong in HTML on top. Also keep canvas.width/height (its real pixel grid) equal to video.videoWidth/videoHeight. CSS size only stretches the picture; if the two grids differ, the dots drift off the joints.

5. What fps means, and what limits it. The readout's fps counts frames that made the whole trip (frame → model → draw) per second. Usually computed as a smoothed average of 1 / (time since the last processed frame). The ceiling is whichever is slowest:

  • The camera. Usually 30 fps. In a dim room many webcams drop to 15, because each frame needs a longer exposure. Practice-room lighting matters.
  • Inference time. recognizeForVideo blocks the main thread. At 45 ms per call you can't exceed about 22 fps, and the page can't respond to anything else meanwhile.
  • Drawing, a busy GPU, heat. A hot laptop slows itself down (thermal throttling). Chrome also throttles background tabs.

fps is not latency. fps is how often you get an update. Latency is how old each update is: light hits the sensor, then capture, inference and display, typically tens of milliseconds to around a tenth of a second. R3 cares about latency ("music reacts with no noticeable extra delay").

In Dance

R1 "done means": mirrored video within a few seconds, skeleton following either hand at about 20+ fps. Expect the R1 branch to use getUserMedia, a video plus canvas stacked in one container, a requestVideoFrameCallback loop, and an fps readout in HTML.

Tradeoff
  • Model on the main thread: simple to write. It blocks the page while it runs, which matters once audio and UI share that thread in R3. The alternative, moving it into a Web Worker, keeps the page responsive but means transferring frames between threads.
  • Higher camera resolution: sharper fingertips at a distance, but more pixels to decode and upload every frame. The landmark model works on a small crop anyway, so extra resolution mainly helps the palm detector spot small, far hands.
The camera delivers 30 fps and each model call takes 45 ms. What will the fps readout show, and what happens to frames that arrive while the model is busy? Does the skeleton fall further and further behind?Reveal

About 22 fps (1000 / 45). Frames that arrive during a call are simply skipped: the video element only keeps the newest one, and the next frame callback fires for whatever frame is presented after you finish.

Nothing queues up, so the skeleton does not drift further behind. Each update is at most one frame plus one inference old. That is a good property of "process the latest frame" loops, compared with a queue that grows whenever processing is slower than input.

4 · Tooling

Vite, TypeScript, Vitest and npm scripts

Problem

Browsers run JavaScript, not TypeScript. They also can't resolve an import like "@mediapipe/tasks-vision", which is a package name, not a URL. And you want to know your finger maths is right without standing in front of a camera.

Mechanism
  • Vite (v8 on the R1 branch). In dev, npm run dev starts a local web server on localhost. When the browser asks for a .ts file, Vite strips the types on the fly with a fast Rust-based transformer (it doesn't type-check), rewrites package imports into URLs it serves from node_modules, and pushes code changes to the open tab over a WebSocket (hot module replacement). vite build bundles and minifies everything into dist/ for a static host.
  • TypeScript (v7, the new natively compiled tsc). It checks types before the code runs, then the types vanish: nothing of them exists at runtime. Types help most at boundaries like the MediaPipe result: the package ships vision.d.ts, so your editor knows result.landmarks[0][8].x is a number. Because Vite never type-checks, the project runs tsc --noEmit separately ("check, don't write files").
  • Vitest (v5). A test runner that reuses Vite's transform, so tests are written in TypeScript with no extra setup. It runs in Node, with no browser and no camera, which is why the finger-state functions should be pure: give them a saved array of 21 points, assert T0 I1 M1 R0 P0.
  • npm scripts are named shell commands in package.json. npm run <name> runs one with node_modules/.bin on the PATH, which is how vite is found without a global install. npm test is a built-in shortcut for npm run test. package-lock.json records the exact version of every installed package, so a fresh install gets the same versions.

The scripts already in the R1 branch's package.json:

"dev": "vite" // local server + hot reload "build": "tsc --noEmit && vite build" // type-check first, then bundle to dist/ "typecheck": "tsc --noEmit" // types only, writes nothing "preview": "vite preview" // serve the built dist/ locally "test": "vitest run" // run tests once and exit
Tradeoff
  • Dev and build take different paths (unbundled vs bundled). That makes dev start instantly, but occasionally something works in dev and breaks in the build. Run npm run build before calling a checkpoint done.
  • Pure functions plus unit tests catch maths bugs cheaply. They can't tell you whether the camera, model and drawing line up; R1's manual "done means" checks cover that.
With npm run dev running, you save a .ts file that has a type error (say, passing a string where a number is expected). Does the page break?Reveal

Usually not. Vite only strips the types; it never checks them, so the page reloads and runs. JavaScript might then misbehave at runtime. The error shows up in your editor, in npm run typecheck, or when npm run build refuses to continue. That's why "build passes" belongs in a ship report.

5 · Preview, not in R1

Coming in R2–R5: turning noisy frames into deliberate controls

R2 · Hold to confirm

Per-frame labels flicker: Victory, Victory, None, Victory, Open_Palm, Victory…. Acting on any single frame would fire commands by accident. Debouncing means acting only on a signal that has stayed stable for a while. The spec's version is a small state machine:

idle ──(shape seen, palm in box)──► arming ──(held 0.6 s)──► fired ──► cooldown 1.0 s ──► idle └──(shape lost longer than a short grace period)──► idle

The grace period forgives a single dropped frame. Hysteresis (two thresholds) keeps pinch from flickering between GRABBED and released. The cost is latency: every command arrives at least 0.6 s after you make the shape.

R4 / R5 · Rate vs position

Two ways to map a hand tilt onto a value.

  • Position control (the "absolute wiper"): the angle is the value. Quick and exact for small ranges, but the whole range must fit in one wrist sweep.
  • Rate control (the "spring-loaded joystick"): the angle sets how fast the value changes. Each frame does value += gain × (angle − centre) × dt. It never runs out of wrist. Because it adds up input over time, it also adds up jitter, so it needs a dead zone: tilts smaller than a few degrees count as zero.

Watch for dt (time since the last frame) in the R4 code. Without it, the knob would move faster on a faster laptop, because fps would change the speed.

Glossary

Terms you'll see in R1 diffs and reports.

landmark
One of the 21 points on a hand that the model outputs, numbered 0 (wrist) to 20 (pinky tip).
normalized coordinates
Positions given as fractions of the image size (0 to 1), not pixels. Multiply by canvas width and height to draw.
world landmarks
The same points in metres in 3D, centred on the hand. Useful for angles; unaffected by how far away you stand.
handedness
The model's Left/Right guess per hand. It assumes a mirrored image, so treat it with suspicion here.
MCP / PIP / DIP / TIP
Knuckle, middle joint, last joint, fingertip. The thumb has CMC, MCP, IP and TIP instead.
canned gesture
One of the Gesture Recognizer's eight built-in labels, such as Victory.
pseudo-chord
Our five-digit finger readout, Thumb to Pinky, 1 = up. Example: 01100 is a V.
inference
Running a trained model on one input to get its output. One frame in, landmarks out.
delegate (GPU / CPU)
Where the model's maths runs: graphics chip through WebGL, or processor through WASM.
WASM (WebAssembly)
A binary code format browsers run at close to native speed. How MediaPipe's C++ runs in Chrome.
.task file
MediaPipe's model bundle (detector, landmark model, classifier), fetched at start-up.
MediaStream
The live camera handle returned by getUserMedia, attached to a video element.
secure context
HTTPS or localhost. Required before the browser will open the camera.
rVFC
requestVideoFrameCallback: run code once for each new video frame.
rAF
requestAnimationFrame: run code before each screen repaint, regardless of video frames.
main thread
The single thread where the page's JavaScript, layout and input handling run. Long work here freezes the page.
fps
Frames fully processed per second. The R1 target is about 20 or more.
latency
Delay from your movement to the screen (or, later, the music) responding. Not the same as fps.
backing store
A canvas's real pixel grid (canvas.width), separate from its CSS display size.
HMR
Hot module replacement: Vite swaps changed code into the open page without a full reload.
bundle
The handful of optimized files vite build produces from many source files.
type erasure
TypeScript types are removed before running; they only exist for checking.
fixture
Saved example input for a test, such as a recorded set of 21 landmarks for a V.
hysteresis
Separate on and off thresholds, so a value near the line doesn't flicker.
debounce / dwell
Act only after a signal has been stable for a set time (0.6 s in R2).
dead zone
A small input range treated as zero, so jitter doesn't move a control.
